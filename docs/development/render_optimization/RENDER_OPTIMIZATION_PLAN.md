# RTSA 渲染优化方案与验证计划

## 1. 文档定位

本文档回答三个问题：

1. 当前仓库中的频谱和瀑布图实际怎样渲染；
2. 哪些性能结论有源码或测试证据，哪些只是历史线索；
3. 下一轮优化应怎样实施和验收，避免把候选方案写成已经完成的结果。

本文档不替代板端测试。所有涉及 ZU47DR、PetaLinux、LinuxFB、DRM/KMS 和 GPU 的结论，都需要在目标板上留存命令输出、运行日志和性能数据。

## 2. 当前实现的源码事实

### 2.1 频谱图：CPU Raster

频谱图由 [`RasterSpectrumRenderer`](../../../src/plot/RasterSpectrumRenderer.cpp) 完成绘制：

- 使用 Qt 的 `QPainter` 在 `QImage` 上进行软件光栅化；
- 静态层 `staticLayer_` 缓存背景、绘图区、网格、坐标轴和静态文字；
- 静态层使用 `QImage::Format_RGB16`；
- 每帧目标图也使用 `Format_RGB16`；
- `renderToImage()` 在目标图尺寸和格式匹配时复用已有缓冲区，否则重新创建；
- 每帧先把静态层复制到目标图，再绘制频谱折线和标记；
- 频谱折线按绘图区列数聚合，当前目标是 `plotRect_.width()` 列；
- 当前代码绘制的是每个聚合列的 `maximum` 折线，`minimum` 仍由包络数据保留但没有单独的填充或竖向包络线绘制；
- 源码没有把折线点数限制为固定的 512 点。

因此，“固定 512 点折线”是可选优化参数，不是当前实现事实。

### 2.2 频谱图：单工作线程和最新帧覆盖

[`SpectrumPlotWidget`](../../../src/plot/SpectrumPlotWidget.cpp) 在构造和析构流程中维护一个离屏渲染工作线程：

1. 新帧到达后，主线程打包 `RenderContext`；
2. `pendingContext_` 被覆盖为最新上下文；
3. 工作线程被唤醒，渲染当前最新上下文；
4. 渲染完成后，在互斥锁保护下发布 `frontImage_`；
5. 主线程收到队列通知，只重绘 `plotRect_` 对应的脏区；
6. 如果没有已完成的离屏图像，`paintEvent()` 会同步调用 `renderer_.paint()` 作为兜底。

这个机制的关键是“单工作线程 + 最新任务覆盖”，不是线程池，也没有按 CPU 核心分配任务。源码注释中出现的并发或性能描述不能替代运行时证据。

### 2.3 频谱图：主线程贴图和静态层复用

离屏图像就绪时，主线程在 `paintEvent()` 中执行切片复制：

```text
painter.drawImage(dirty.topLeft(), frontImage_, dirty)
```

它避免了主线程重新计算折线和重新绘制静态标尺。当前仍存在的成本包括：

- 工作线程每帧复制整幅静态层；
- 目标图尺寸跟随整个控件，而不是只跟随绘图区；
- 主线程的贴图、窗口合成和 Framebuffer 提交仍需计入端到端时间；
- 新 `RenderContext` 到达时只保留最新任务，因此输入帧率较高时会主动合并中间帧。

合并中间帧可以降低积压风险，但不等于零丢帧，也不等于固定显示帧率。

### 2.4 瀑布图：索引色环形缓冲区

[`WaterfallPlotWidget`](../../../src/plot/WaterfallPlotWidget.cpp) 使用 `QImage::Format_Indexed8` 保存历史行：

- 默认历史深度为 512 行，配置范围为 64 至 2048 行；
- 新帧写入单行，使用环形头指针推进；
- 绘制时把跨越环形边界的历史拆成两个源矩形；
- 尺寸或行数变化时重建历史图像。

该路径减少了颜色通道数据量，但仍有图像写入、颜色表/显示格式转换、QPainter 绘制和 Framebuffer 提交成本。文档中不应把它写成“完全零转换”。

### 2.5 当前未实现的优化

以下内容目前不能写成已完成：

- 多线程频谱渲染线程池；
- CPU 亲和性或固定的核心分工；
- 基于 GPU 的频谱绘制；
- 将一个周期固定压到某个毫秒数；
- 在所有板端配置下稳定达到 60 FPS；
- 24 小时长稳、绝对幅度标定或 DMA 硬件链路验证。

## 3. 证据分级

| 级别 | 证据 | 可以怎样表述 |
| :--- | :--- | :--- |
| A | 当前源码、当前 CMake 配置 | “已实现”“当前路径”“源码中不存在” |
| B | 指定日期、指定构建和指定环境的测试记录 | “在该环境下测得”，并附测试条件 |
| C | 早期观察或未保存原始日志的数据 | “历史线索，待复测”，不能作为当前结论 |
| D | 硬件预期、设计推导、候选方案 | “预计”“可能”“需在板端验证” |

### 3.1 PC 历史结果

历史记录中曾有一组 Windows、Qt 6、Release 构建的模拟源结果：

- 频谱点数：16,384；
- 请求输入帧率：1,000 FPS；
- 输入统计约 1,000 FPS；
- 显示统计约 33.7 FPS；
- 显示 P95 延迟约 16.5 ms。

这组数据只能说明该历史 PC 环境中的表现。它没有自动证明当前源码、当前测试集、当前窗口尺寸或 ZU47DR 板端能达到相同结果。引用时必须同时写明平台、构建类型、测试日期和参数。

### 3.2 板端早期线索

早期材料曾记录过较低的显示帧率、数十毫秒级的绘制耗时和某个 CPU 核心占用偏高等现象，但当前仓库没有同时提供完整原始日志、固定测试参数和可重复的对照步骤。因此这些数字只能用于安排复测，不能作为当前版本的性能基线，也不能直接推出某个优化必然有效。

## 4. 先测量，再优化

### 4.1 必须采集的指标

每次测试至少记录：

- 输入帧率、实际发布帧率和显示帧率；
- `SpectrumPlotWidget::lastPaintMilliseconds()`；
- `isLastPaintOffscreen()`，用于区分离屏贴图和同步兜底；
- 显示延迟和显示 P95；
- 跳过/丢弃帧计数；
- 纯频谱、纯瀑布图和频谱+瀑布图三种视图的结果；
- 进程总 CPU、各 CPU 核心、内存和线程数量；
- Qt 版本、QPA、屏幕分辨率、Framebuffer/DRM 格式；
- 窗口尺寸、频谱点数、输入帧率和色图/线宽设置。

`lastPaintMilliseconds()` 只覆盖一次 `paintEvent()` 的耗时，不等于工作线程的渲染耗时，也不等于从采集到屏幕显示的端到端延迟。若要判断瓶颈，需要同时记录工作线程渲染时间和提交时间。

### 4.2 固定测试矩阵

建议先固定以下变量，再做前后对比：

| 变量 | 基线建议 |
| :--- | :--- |
| 数据源 | 模拟源，固定场景 |
| 频谱点数 | 16,384（另测 4,096 和 65,536） |
| 输入帧率 | 100 FPS、500 FPS、1,000 FPS |
| 窗口尺寸 | 目标板实际全屏尺寸和一个固定小窗口 |
| 视图 | 仅频谱、仅瀑布图、频谱+瀑布图 |
| 曲线设置 | 固定颜色、线宽和网格开关 |
| 运行时长 | 先做短测，再进行独立的长稳测试 |

当前 CTest 注册了 15 项测试，其中包含 `rtsa_waterfall_tests`。仓库中的历史 `14/14` 记录对应旧测试集，不能当作当前 15 项测试的结果。本文档整理过程中没有重新构建或运行 CTest。

## 5. 候选优化方案

以下方案按风险和验证成本排序。它们尚未在本轮文档整理中实现，也没有板端收益数据。

### 5.1 方案一：完善测量和任务合并可视性

**目的**：避免在没有数据的情况下增加并发复杂度。

建议增加或汇总以下诊断信息：

- 工作线程实际渲染耗时；
- 每帧复制静态层的耗时；
- `RenderContext` 被新任务覆盖的次数；
- 静态层重建次数；
- 主线程贴图耗时和 Framebuffer 提交占比；
- 输入、发布、显示三个阶段的序列号差。

**验收**：同一输入下，指标能够稳定重复；优化前后使用相同测试配置。

### 5.2 方案二：按可视像素设置折线聚合预算

当前聚合列数等于 `plotRect_.width()`，没有 512 点上限。可以考虑把目标列数设为一个有上限、可配置的值，例如：

```text
targetColumns = min(plotWidth, columnBudget)
```

但必须先验证：

- 峰值和窄信号是否仍能在屏幕上定位；
- 聚合是否保留每列的最大值，必要时是否同时保留最小值；
- Marker、峰值搜索和实际 bin 坐标是否仍正确；
- 不同宽度和缩放下是否出现明显视觉跳变。

这项优化只减少几何图元数量，不保证固定比例的帧率提升。

### 5.3 方案三：减少每帧静态层复制

当前频谱工作线程每帧把整幅静态层复制到目标图。可评估：

- 只维护绘图区的静态背景；
- 将历史波形和静态层分离，按脏区恢复背景；
- 对未变化的区域复用上一帧切片；
- 根据屏幕格式选择匹配的 `QImage` 格式，避免额外转换。

任何方案都必须验证局部更新不会留下旧波形、标记残影或在缩放时出现错位。

### 5.4 方案四：核对 LinuxFB 与 DRM/KMS 显示路径

先用 [GPU 与 QPA 核验指南](./GPU_VERIFICATION_GUIDE.md) 确认板端实际路径：

- LinuxFB：检查 `/dev/fb*`、颜色格式、分辨率和 Framebuffer 写入方式；
- DRM/KMS：检查驱动、connector、Qt 插件和 page flip；
- EGLFS/OpenGL ES：只有确认 GPU、EGL 和驱动可用后才作为候选。

切换显示后端前应先做纯显示压力测试，把 RTSA 绘制耗时与显示提交耗时分开，避免把 Framebuffer 或 VSync 的限制误判为频谱算法瓶颈。

### 5.5 方案五：谨慎评估并发

当前只有一个离屏工作线程。只有在测量证明工作线程是主要瓶颈，并且主线程仍有余量时，才考虑增加固定的并行阶段或第二个渲染 worker。

不建议直接引入“四核线程池”或给线程绑定 CPU，因为：

- `QPainter` 访问共享图像时需要明确的所有权和同步边界；
- 线程数量增加会带来上下文切换、内存带宽和调度抖动；
- 板端其他任务、内核显示线程和 DMA 线程也需要 CPU；
- 没有板端数据时无法证明固定核心分工能改善端到端延迟。

### 5.6 方案六：条件性使用显示或硬件加速

DRM/KMS、PL 端二维绘图和 Web/B-S 分离显示都属于候选架构：

- DRM/KMS 需要可用的 DRM 驱动、显示控制器和 Qt 插件；
- PL 加速需要 RTL、驱动、内存带宽和同步设计；
- Web 渲染需要稳定的网络链路和 PC 端软件。

这些方案在没有原型和对照数据前，不应写入固定 FPS、固定 CPU 降低比例或“彻底消除撕裂”等结论。

## 6. 板端验收流程

### 6.1 启动前

1. 记录构建版本和启动参数；
2. 记录 Qt 版本、QPA、插件路径；
3. 记录屏幕分辨率、Framebuffer/DRM 节点和格式；
4. 运行 [GPU 与 QPA 核验指南](./GPU_VERIFICATION_GUIDE.md) 中的检查命令；
5. 确保测试源和场景与基线一致。

### 6.2 运行中

1. 先观察纯频谱视图，再观察纯瀑布图，最后观察组合视图；
2. 每种组合至少运行足够长时间以覆盖启动、稳定和交互阶段；
3. 记录正常状态和窗口缩放、Marker 操作、视图切换后的表现；
4. 保存日志和统计信息，不只记录一张截图或单个瞬时 FPS；
5. 如果发生回退到同步绘制，保存 `isLastPaintOffscreen()` 或对应日志证据。

### 6.3 通过条件

一个优化只有在以下条件同时满足时才算通过：

- 频谱、瀑布图和 Marker 的视觉结果正确；
- 峰值和窄信号的定位没有被聚合策略不可接受地改变；
- 不存在持续积压、崩溃、内存增长或明显画面撕裂；
- 显示帧率或端到端延迟在重复测试中有稳定改善；
- 性能提升不是通过丢弃必要的显示更新或隐藏错误得到的；
- 测试环境、原始数据和失败案例都被记录。

目标帧率应由产品需求和实际屏幕能力确定，不能把“60 FPS”当成未经确认的验收事实。

## 7. 推荐推进顺序

| 阶段 | 工作 | 产出 |
| :--- | :--- | :--- |
| 0 | 复测当前板端基线 | 环境、命令、日志、FPS、延迟、CPU 分布 |
| 1 | 完善诊断指标 | 可区分工作线程、主线程和显示提交的成本 |
| 2 | 实施低风险 CPU Raster 优化 | 折线预算、静态层/脏区复用的前后对照 |
| 3 | 验证显示后端 | LinuxFB 与可用 DRM/KMS 路径的对照结果 |
| 4 | 评估并发或 PL/Web 方案 | 仅在阶段 1 至 3 证明有必要时进入原型 |
