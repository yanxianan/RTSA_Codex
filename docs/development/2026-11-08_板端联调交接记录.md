## 1. 当前结论

本轮已经完成中文显示修复，并把 DMA 无数据问题缩小到两个独立层面：

1. **操作层面已确认**：加载新 bitstream 会清掉 AXI DMA 的 IRQ 使能位。必须在加载 bitstream 后重新加载 `rtsa_dma.ko`，否则首帧完成后 `IOC=1` 但 CPU 收不到中断，描述符不会回收。
2. **PL 数据通路仍未跑通**：重新加载驱动后 `DMACR` 已恢复 IRQ 使能，但 PL 没有送出完整的 2112 字节频谱帧。配置 commit 一直停在 `config_busy=1`，说明 `pl_config_latch` 等不到帧边界，`spectrum_frame_builder` 很可能卡在 HEADER/PAYLOAD 中间。

因此当前不是“驱动没启动”或“DDS 没配置”的问题，而是 **PL 组帧器没有完成一帧**，或 **AXIS FIFO→DMA 的接收侧没有真正放行**。下一步需要加 PL 调试寄存器或接 JTAG ILA，不能再靠猜。

## 4. UIO `rtsa_regs`：根因已确认，DTS 已改，尚未重新编译 DTB

### 4.1 现象

板端只有 `uio0~uio3`（axi-pmon），没有 `rtsa_regs`。应用日志：

```text
[DMA] 未找到 rtsa_regs UIO，使用 PL 默认配置
```

### 4.2 根因

内核 `uio_pdrv_genirq` 读取的属性名是 **`linux,uio-name`**，不是 `uio-name`。设备树里写的是：

```dts
uio-name = "rtsa_regs";
```

所以即使设备已经绑定，UIO 名字也只是默认的 `axi_bram_ctrl`，应用按名字找不到。

另外，首次手动 bind 时设备处于 `waiting_for_supplier`，说明时钟依赖尚未解析完成；等待后 `waiting_for_supplier=0`，再用 `driver_override` 强制绑定成功，生成 `uio4`，名字为 `axi_bram_ctrl`。

### 4.3 已修改

`driver/DMA/system-user.dtsi` 已改为：

```dts
&axi_bram_ctrl_0 {
    compatible = "generic-uio";
    linux,uio-name = "rtsa_regs";
    status = "okay";
};

&usp_rf_data_converter_0 {
    compatible = "xlnx,usp-rf-data-converter-2.6";
    linux,uio-name = "uio4";
    uio-offset = <0x40000>;
    interrupts = <0 89 4>;
};
```

### 4.4 下次要做的

1. 用该 DTS 重新编译并更新板端 DTB。
2. 重启后确认：

```bash
for f in /sys/class/uio/uio*/name; do echo "$f: $(cat "$f")"; done
```

应出现：

```text
.../uio4/name: rtsa_regs
```

3. 如果仍不自动绑定，检查：

```bash
cat /sys/bus/platform/devices/a0000000.axi_bram_ctrl/waiting_for_supplier
cat /sys/bus/platform/devices/a0000000.axi_bram_ctrl/driver_override
readlink -f /sys/bus/platform/devices/a0000000.axi_bram_ctrl/driver
```

必要时临时测试：

```bash
echo uio_pdrv_genirq > /sys/bus/platform/devices/a0000000.axi_bram_ctrl/driver_override
echo a0000000.axi_bram_ctrl > /sys/bus/platform/drivers/uio_pdrv_genirq/bind
```

## 5. DMA 无数据：已确认的两个层面

### 5.1 关键地址

```text
PL 寄存器基址       0xA0000000
AXI DMA 基址        0xA0080000
S2MM_DMACR          0xA0080030
S2MM_DMASR          0xA0080034
S2MM_DA（简单模式） 0xA0080048
S2MM_LENGTH         0xA0080058
```

PL 关键寄存器：

```text
0x100 center low
0x108 span low
0x11C config epoch staging
0x120 commit
0x130 config busy
0x134 active epoch
0x20C CIC rate
0x210 DMA mode
0x218 HB level
0x224 Max Hold frames
```

### 5.2 已确认：重启后不会自动加载新 bitstream

重启后 `devmem 0xA0000210` 等寄存器全为 `0`，说明 PL 没有配置成当前设计。手动加载：

```bash
fpgautil -b /home/root/DMA_TOP_20261106a.bit -f Full -n full
```

加载后读回：

```text
0x210 = 0x00000001   DDS
0x20C = 0x00000008   CIC=8
0x218 = 0x00000002   HB=2
0x224 = 0x00000050   Max Hold=80
0x134 = 0x00000001   active epoch
```

说明加载后的 PL 默认配置正确。

### 5.3 已确认：bitstream 加载后必须重载 DMA 驱动

不重载驱动时：

```text
S2MM_DMACR = 0x00010003
S2MM_DMASR = 0x00001002   # IDLE + IOC 挂起
```

`DMACR` 的 `0x7000`（IOC/DLY/ERR IRQ 使能）为 0，所以完成事件不会送到 CPU；`/proc/interrupts` 不增长，描述符不回收。

执行：

```bash
rmmod rtsa_dma
insmod /home/root/rtsa_dma.ko
```

后：

```text
S2MM_DMACR = 0x00037003   # 0x7000 IRQ 使能已恢复
```

`/proc/interrupts` 的 `xilinx-dma-controller` 开始计数。

**原因**：Linux 启动/驱动 probe 发生在 PL 配置之前，之后 `fpgautil` 重配置 PL 会把 AXI DMA 的 `DMACR` 清掉；驱动的 `RTSA_IOC_START` 只置 RUNSTOP，不会重新置 IRQ 使能位。

**临时规避**：每次加载 bitstream 后重新加载 `rtsa_dma.ko`。

已新增脚本：

```bash
sh driver/DMA/load_bitstream_and_reload_dma.sh /home/root/DMA_TOP_20261106a.bit
```

**根治建议**（下次做）：

- 在驱动 `RTSA_IOC_START` 中显式写 `DMACR |= 0x00007000`，不要依赖 probe 时的寄存器状态；或
- 保证板端启动流程先加载 bitstream，再加载 `rtsa_dma.ko`。

### 5.4 仍未解决：PL 没有送出完整帧

重载驱动后继续测试：

```text
S2MM_DMACR = 0x00037003
S2MM_DMASR = 0x00000000
S2MM_LENGTH = 0x00000840   # 2112 字节，仍未被消费
/proc/interrupts xilinx-dma-controller 计数不再增长
```

应用日志仍然只有：

```text
[DMA] RTSA_IOC_START 启动成功，进入采集循环...
显示: 0.0 FPS ...
```

没有 `[DMA] 首帧捕获成功`，也没有 `[DMA 运行状态]`。

### 5.5 关键判据：配置锁存卡在帧边界

在 DMA 运行状态下写：

```bash
devmem 0xA000011C 32 0x2222
devmem 0xA0000120 32 1
sleep 1
devmem 0xA0000130 32
devmem 0xA0000134 32
```

结果：

```text
0x130 = 0x00000001   config_busy 一直为 1
0x134 = 0x00000001   active epoch 仍为 1，没有变成 0x2222
```

`pl_config_latch` 在 `S_WAIT` 等 `frame_idle || frame_complete`。现在一直等不到，说明 `spectrum_frame_builder` 不在 `ST_IDLE`，而是卡在 `ST_HEADER` 或 `ST_PAYLOAD`。

结合 `S2MM_LENGTH` 一直为 2112、DMA 无完成，最可能的情况是：

- 组帧器已进入 HEADER，但 `m_axis_tready` 一直为 0；或
- 组帧器进入 PAYLOAD 后，`fft_max_hold` 的输出没有继续给出 1024 个频点，导致 `fifo_count<4`、`m_axis_tvalid=0`，帧永远不产生 `TLAST`。

### 第二步：加 PL 调试寄存器（最直接）

建议在 `axi_bram_ctrl` 的 `0x140~0x15C` 增加只读调试快照：

```text
0x140  r_clk 自由计数低 32 位
0x144  {frame_idle, frame_complete, config_busy, active_dma_mode}
0x148  {m_axis_data_tvalid, m_axis_data_tready,
        spectrum_frame_tvalid, spectrum_frame_tready}
0x14C  {builder_state[1:0], header_index[3:0],
        beat_count[15:0], fifo_count[4:0]}
0x150  {fft_raw_tvalid, fft_raw_tready, frame_valid, dec_valid}
0x154  dec_valid / frame_valid / fft_raw_tvalid / m_axis_data_tvalid 计数器
0x158  dds_valid / cic_busy / source_enabled
```

这些信号在 `logic_clk` 域，进 `axi_bram_clk` 前做两级同步即可。读一次就能判断：

- `r_clk` 是否在跑；
- 组帧器到底停在 HEADER 还是 PAYLOAD；
- `m_axis_tready` 是否为 0；
- `fft_raw_tvalid` 是否停止；
- `dec_valid` 是否停止。

### 第三步：隔离 AXIS FIFO

`axis_data_fifo_0` 当前是 `FIFO_MODE=2`（store-and-forward），只有收到 `TLAST` 才整包转发。若组帧器卡在包中间，DMA 侧会一直看不到数据。可以临时改成 cut-through，或加一个旁路开关，直接验证 `spectrum_frame_builder -> DMA`。

### 第四步：JTAG ILA（如果以后接 JTAG）

本次用户明确没有连接 JTAG，`hw_server` 无 target，无法抓 ILA。以后接 JTAG 后优先看：

```text
r_clk / r_rst
dds_valid / dec_valid
fft_raw_tvalid / fft_raw_tready
builder state / m_axis_tvalid / m_axis_tready / m_axis_tlast
```
