### 解决方案与修复步骤

#### 方案一：修复设备树（若 RJ45 对应 GEM3 + DP83867 PHY 芯片）

需要在设备树中干掉 `fixed-link`，补全标准 `mdio` 子节点与 DP83867 驱动节点。

通过串口在开发板上直接执行以下命令重新生成 dtb 测试：

```bash
# 1. 备份原启动 dtb
cd /run/media/boot-mmcblk1p1
cp system.dtb system.dtb.bak

# 2. 反编译当前 dtb 为 dts
dtc -I dtb -O dts system.dtb -o /tmp/fix.dts
```

在 `/tmp/fix.dts` 中找到 `ethernet@ff0e0000`，修改为规范的 MDIO 模式（删除 `fixed-link`，添加 `mdio` 节点）：

```dts
ethernet@ff0e0000 {
    compatible = "xlnx,zynqmp-gem\0cdns,gem";
    status = "okay";
    reg = <0x00 0xff0e0000 0x00 0x1000>;
    phy-mode = "sgmii";
    local-mac-address = [00 0a 35 00 22 05];
    phy-names = "sgmii-phy";
    phys = <0x14 0x03 0x08 0x03 0x00>;
    phy-handle = <&phy0>;

    /* 必须包裹在 mdio 节点中，且不要 fixed-link */
    mdio {
        #address-cells = <1>;
        #size-cells = <0>;
        phy0: phy@c {
            reg = <0x0c>;
            ti,rx-internal-delay = <0x08>;
            ti,tx-internal-delay = <0x0a>;
            ti,fifo-depth = <0x01>;
            ti,rxctrl-strap-worka;
        };
    };
};
```

编译并放回启动分区：
```bash
dtc -I dts -O dtb /tmp/fix.dts -o /run/media/boot-mmcblk1p1/system.dtb
sync
reboot
```

  - **开发板 ZU47DR 与 SFP 模块之间（内部 SerDes 端）**：SGMII / SerDes 协议握手**失败**，开发板 MAC 控制器（GEM3）的 PCS 物理编码子层无法与模块内部的 PHY 达成链路同步，因此 Linux 内核报 `NO-CARRIER`。

### 3. 具体如何排查与解决（按优先级排列）

#### 排查一：协议模式错配（概率 60%，最快解决）
千兆 SFP 电口模块在 SerDes 侧通常分两种模式：
- **1000BASE-X 模式（纯千兆光口协议，无 SGMII 自协商）**
- **SGMII 模式（依赖 SGMII 自协商）**

当前设备树配置为 `phy-mode = "sgmii"` 并搭配 `fixed-link`，内核驱动没有配置 PCS 自协商。若你的 SFP 电模块是 1000BASE-X 模式，两边协议不兼容就会永远报 `NO-CARRIER`。

DisplayPort 接口由两条通道组成：
1. **AUX 辅助通道（低速控制线）**：
   - 负责读取显示器的 EDID 身份信息。

2. **Main Link 主链路（高速视频数据线）**：

```

   PS-GTR SerDes┤
 (高速收发器子系统)└─── Lane 3 ──────────► SFP 千兆网口     (报错: NO-CARRIER)
```

- **SFP 千兆网口**：走 PS-GTR 的 **Lane 3**（依赖 GTR SGMII 时钟与通道）

现在的情况是：**整个 PS-GTR 在当前系统下都没有正常工作！**

导致 PS-GTR 整体失效的根本原因：
1. **外部时钟芯片或参考时钟未起振**：
   开发板上的 GTR 参考时钟（如 27MHz / 125MHz）通常是由板载可编程时钟芯片（如 SI5341 / CDCE925 等）提供的。如果当前的 `system.bit`（PL端）或者 `BOOT.BIN`（FSBL）中没有正确初始化时钟芯片，GTR 没有参考时钟输入，SerDes PLL 无法锁定，DP 无法训练链路，网口也无法接收信号。
2. **当前 Vivado 导出的 XSA / FSBL 配置有误**：
   当前重新搭建系统使用的 `BOOT.BIN` 是今天新编译的，其 FSBL 中的 GT/SerDes 初始化参数与 7 月 31 日正常系统的工程存在差异。

### 为什么会网口（SFP）和显示器（DP）“同时死掉”？

因为它们在底层有着完全相同的硬件命门——**PS-GTR 高速 SerDes 收发器**：
- **DP 显示**：走 PS-GTR **Lane 0 & Lane 1**
- **SFP 网口**：走 PS-GTR **Lane 3**

在 Vivado 逻辑端，导致整组 GTR 高速外设瘫痪的**最大概率问题**有以下 3 个（按概率由高到低）：

---

#### 1. 最大概率（85%）：Vivado 中 PS-GTR 的“参考时钟源（RefClk）”或“频率”配置错位
在 Vivado 打开 Block Design 双击 `Zynq UltraScale+ MPSoC` IP 核：
进入 **I/O Configuration -> High Speed Connectivity**：

```
[GTR Lane 0/1 (DP)]   ──► 必须绑定外部引脚: GTR_REF_CLK0 (通常为 27MHz)
[GTR Lane 3 (GEM3)]   ──► 必须绑定外部引脚: GTR_REF_CLK3 或 GTR_REF_CLK1 (通常为 125MHz)
```

**问题往往出在：**
- 新工程里，某个 Lane 的 **`Ref Clock` 下拉框选错了**（例如把 DP 或 SGMII 选到了板上未连线的 REF_CLK，或者多个 Lane 抢了同一个时钟）；
- 或者在 **Clock Configuration** 页面里，输入的参考时钟实际频率（Frequency）填错了；
- **后果**：Vivado 导出的 FSBL 初始化代码（`psu_init.c`）计算出的 PLL 倍频与分频参数全错，GTR 的 PLL 根本无法锁定，导致 **DP 主链路训练失败（黑屏）**、**网口收发器无载波（NO-CARRIER）**。

---

#### 2. 次大概率（70%）：板载可编程时钟芯片的 PL 端 I2C 初始化逻辑丢失
像 **ZU47DR / CoreBoard V2** 这种高端 RFSoC 板卡，提供给 PS-GTR 的 27MHz 和 125MHz 参考时钟，**通常不是直接接固定晶振，而是由板载的外部可编程时钟芯片（如 Silicon Labs SI5341 / SI5324 等）生成的**。

在很多参考设计中：
- 芯片上电时，外部时钟芯片默认是不输出时钟的；
- **需要在 PL 端（system.bit）跑一段 Verilog/VHDL 逻辑或者 AXI-I2C 模块，在开机第一时间通过 I2C 向该芯片配置寄存器，时钟芯片才开始输出 27MHz 和 125MHz**。
- **排查点**：对比新旧 Vivado 工程的顶层文件（Top module）或 Block Design，看是否新工程漏掉了时钟芯片的初始化逻辑/IP，或者 XDC 里把时钟芯片的 I2C 管脚给漏掉了。

---

#### 3. 常见细节遗漏（40%）：SFP 笼子的 `TX_DISABLE` 管脚在 XDC 中未约束/未拉低
SFP 笼子的 Pin 3（`TX_DISABLE`）通常连在 FPGA 的 PL 引脚上。
- SFP 规范要求该引脚必须为 **低电平（0）** 模块才允许发射。模块内部自带弱上拉电阻。
- 如果新工程的 Verilog 代码中漏掉了 `assign sfp_tx_disable = 1'b0;`，或者 XDC 约束中没有约束该管脚，这个引脚就会处于三态输入（悬空），模块内部上拉强行把发射端关闭，导致网卡始终 `NO-CARRIER`。
