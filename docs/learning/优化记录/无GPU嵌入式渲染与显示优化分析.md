## 1. 结论摘要

当前程序已经采用了 CPU Raster、静态层缓存、包络降采样、单后台渲染线程、最新帧覆盖、RGB16 图像和脏区贴图等措施，但这条路径仍有明确的继续优化空间。收益最大且风险最低的方向不是再次增加线程，而是先减少图像缓冲区的重复复制、减少瀑布图在 GUI 线程中的整图重绘，并用板端数据判断“同步直绘”和“后台离屏”哪一个更适合当前硬件。

建议优先处理以下五项：

1. **修复 QImage 写时复制导致的隐式 `detach()`**：当前后台线程发布 `frontImage_` 后，下一次继续写 `localBackBuffer` 会触发共享数据分离，可能每帧重新分配并复制整幅图像。应改为真正的 Ping-Pong 缓冲区交换。
2. **频谱每帧只恢复绘图区静态背景**：当前 `renderToImage()` 每帧复制整个频谱控件大小的静态层，而实际动态变化的区域只有 `plotRect_`。可先保持成品图仍为控件大小，但只复制绘图区背景。
3. **缓存瀑布图静态元素并减少重复转换**：当前网格、坐标文字、色标和 `1×256` 色条图像都在 GUI 线程中反复绘制；`Indexed8` 历史图在每次 `paintEvent()` 中还要缩放并转换到 RGB16 目标。
4. **增加可实测的 `direct / offscreen` 渲染模式和诊断指标**：历史板端记录表明后台离屏不一定比同步绘制快，必须用同一版本、同一场景做 A/B，而不能继续假设“多线程一定优于单线程”。
5. **把显示刷新上限与输入帧率解耦**：当前 10 ms 定时器最多尝试 100 Hz 显示，但并未与屏幕刷新、渲染完成或 Framebuffer 提交同步。应支持 30/60 Hz 等可配置上限，并只保留一个待处理渲染任务。

不推荐把“增加多个渲染 worker”或“CPU 绑核”作为第一步。当前频谱只产生一个连续绘制任务，`QPainter` 对单幅 `QImage` 的光栅化基本是串行过程；在没有测量出具体瓶颈前增加线程，可能只增加锁竞争和内存带宽压力。

建议的最终目标是：

```text
采集与处理线程
  -> LatestFrameStore
  -> 可配置显示调度（30/60 Hz）
  -> 频谱：Ping-Pong 离屏或同步直绘（由板端 A/B 决定）
  -> 瀑布图：静态层缓存 + 预量化 RGB16 历史缓存
  -> GUI 只做一次合成与脏区提交
  -> 先使用 LinuxFB；只有数据证明 QPA 合成是主瓶颈时，
     再原型验证 DRM/KMS page flip 或自定义 Framebuffer 后端
```

本方案不会把 OpenGL ES2 重新引入当前平台。目标板没有可用于通用图形渲染的 GPU，软件 OpenGL 只会把更多工作重新压回 CPU。

## 3. 目标平台和 2K 显示成本

### 3.1 硬件约束

当前项目按以下约束设计：

- ZU47DR PS 端为 ARM Cortex-A53 多核 CPU；
- 没有可用于 Qt OpenGL/EGL 通用渲染链路的外接或内置 GPU；
- 显示输出通过板端 Linux 显示驱动和 Qt QPA 完成；
- 历史运行方式为 `linuxfb:fb=/dev/fb0`；
- 历史显示信息为 `2560×1440`、16 bpp、RGB565；
- 上述 Framebuffer 信息仍需在当前 rootfs 和目标 bit 上复测。

无 GPU 并不意味着只能接受低帧率。真正需要优化的是 CPU 光栅化、图像复制、格式转换和显示合成，而不是简单地“把所有工作移到更多线程”。

### 3.2 2K 像素与带宽预算

对于 `2560×1440` Framebuffer：

```text
RGB16 单幅图像：
2560 × 1440 × 2 = 7,372,800 bytes ≈ 7.03 MiB

ARGB32 单幅图像：
2560 × 1440 × 4 = 14,745,600 bytes ≈ 14.06 MiB

RGB16 在 30 FPS 下的单次全屏写入量：
7,372,800 × 30 ≈ 221 MB/s

RGB16 在 60 FPS 下的单次全屏写入量：
7,372,800 × 60 ≈ 442 MB/s
```

若频谱控件在全屏“仅频谱”模式下接近整屏大小，应用前后缓冲、静态层、Qt backing store、QPA 合成图和 Framebuffer 可能同时占用约 6 幅 RGB16 图像，总量达到约 `42 MiB`。这不是精确实测值，但足以说明：

- 分辨率提高会按面积而不是按边长增加成本；
- 每减少一次全屏复制，都会同时减少 CPU 周期和内存带宽消耗；
- 在 60 FPS 下，多次全屏复制很容易进入数 GB/s 的总内存流量；
- 继续提高“显示定时器频率”不能替代减少复制次数。

### 3.3 分辨率变更是否会导致不可预料的问题

当前频谱和瀑布图的图像尺寸、包络列数、绘图区矩形和瀑布历史宽度均由控件实际尺寸动态计算，因此不是把 `2560×1440` 写死在渲染算法中。更换显示器后，程序理论上不会因为分辨率变化直接失效，但以下内容会改变：

- 静态层和前后缓冲的内存占用；
- 每帧静态背景复制量；
- 包络折线顶点数；
- 瀑布图的调色板转换和缩放成本；
- LinuxFB 全屏合成量；
- 字体、DPI、逻辑窗口尺寸和响应式布局断点；
- 端到端延迟和可达到的显示帧率。

因此，问题不是“换分辨率必然产生随机故障”，而是“当前实现和性能结论具有明显的分辨率相关性”。需要在 `2560×1440`、`1920×1080` 和至少一个较低分辨率上重复同一组测试，不能只验证开发机上的窗口尺寸。

## 4. 当前频谱渲染链路

### 4.1 数据与显示主路径

当前源码中的频谱路径为：

```text
采集线程
  -> SpectrumPipeline
  -> LatestFrameStore
  -> MainWindow 每 10 ms 读取最新帧
  -> SpectrumPlotWidget::setFrame()
  -> 覆盖 pendingContext_
  -> 单个 renderWorker_
  -> RasterSpectrumRenderer::renderToImage()
  -> QImage::Format_RGB16 frontImage_
  -> paintEvent() 按脏矩形贴图
```

关键源码：

- `src/ui/MainWindow.cpp:204-208`：`Qt::PreciseTimer`，间隔 10 ms；
- `src/ui/MainWindow.cpp:415-434`：读取 `pipeline_.latest()`，同序号跳过；
- `src/plot/SpectrumPlotWidget.cpp:433-469`：单个后台工作线程和最新任务覆盖；
- `src/plot/SpectrumPlotWidget.cpp:392-421`：GUI 线程脏区贴图和同步兜底；
- `src/plot/RasterSpectrumRenderer.cpp:122-150`：每帧复制静态层并绘制动态内容；
- `src/core/EnvelopeReducer.cpp:9-50`：按屏幕列执行 min/max 包络压缩。

### 4.2 当前频谱渲染的职责划分

`RasterSpectrumRenderer` 的静态层包含背景、绘图区底色、网格、边框、幅度刻度、频率刻度、中心频率与 Span 标题以及幅度单位。每帧动态内容主要包括频谱折线、最多 4 个 Marker、Marker 三角和标签。

静态层和成品图都使用 `QImage::Format_RGB16`，方向与历史 LinuxFB 的 RGB565 路径匹配。但格式匹配只消除了“像素格式转换”，并不能消除图像复制。

### 4.3 包络几何

`EnvelopeReducer::reduce()` 根据绘图区宽度把全部频点聚合为若干列，每列保留最小值和最大值。当前绘制路径只使用每列的 `maximum` 形成折线：

```text
目标列数 = min(频点数, plotRect.width())
参与折线绘制的点 ≈ plotRect.width()
```

源码没有固定为 512 点。把列数强制降到 512 会减少一部分折线顶点，但也可能降低窄峰和噪声底的表现力，因此只能作为测量后的可选项，不能预先当作主要优化。

### 4.4 后台工作线程的真实语义

`SpectrumPlotWidget` 只启动一个 `std::thread`。`pendingContext_` 永远只保存一个最新任务，新帧到达时覆盖尚未处理的旧任务。这个设计有利于限制延迟和内存，但不是线程池，也没有 CPU 亲和性。

`src/plot/SpectrumPlotWidget.h:130` 和 `.cpp:35` 中的“多核异步”注释属于历史描述，不能据此认为频谱渲染已经使用多核并行。

## 5. 当前瀑布图渲染链路

瀑布图使用 `QImage::Format_Indexed8` 保存历史行。新行写入是单行操作，稳态下不会整体搬移历史数据，这部分设计是合理的。

但是，当前 `WaterfallPlotWidget` 仍在 GUI 线程完成以下工作：

1. `addFrame()` 对完整频点执行逐列峰值降采样；
2. 将每列幅度映射为 0～255 的颜色索引；
3. 写入环形缓冲；
4. `paintEvent()` 填充整个控件背景；
5. 每帧对 `Indexed8` 历史图执行缩放和调色板到目标格式的转换；
6. 每帧重新绘制网格、边框、频率轴、时间轴和色标文字；
7. 每帧重新创建 `1×256` 的色条图像。

关键源码：

- `src/plot/WaterfallPlotWidget.cpp:198-242`：GUI 线程中的降采样和颜色索引映射；
- `src/plot/WaterfallPlotWidget.cpp:250-274`：忽略事件脏矩形，每次重画整个瀑布控件；
- `src/plot/WaterfallPlotWidget.cpp:277-319`：每次创建色条图像；
- `src/plot/WaterfallPlotWidget.cpp:321-360`：每帧从 `Indexed8` 绘制并缩放历史图；
- `src/plot/WaterfallPlotWidget.cpp:363-429`：每帧重画网格和全部文字。

瀑布图每来一帧，屏幕内容都会发生纵向滚动，因此“只重绘一行”不能直接等价为“只更新一个小脏区”。但静态色标、坐标文字和背景仍可以缓存，`Indexed8 -> RGB16` 的逐像素转换也可以提前完成。

## 6. Qt 5.15 LinuxFB 显示链路

根据 Qt 5.15 的 LinuxFB/FB convenience 源码，常规路径大致为：

```text
控件 paintEvent()
  -> QFbBackingStore 窗口图像
  -> QFbScreen 合成图像 mScreenImage
  -> QLinuxFbScreen::doRedraw()
  -> mmap 映射的 /dev/fb0
```

Qt 5.15 的 `QFbBackingStore` 使用屏幕 QPA 报告的目标格式创建窗口图像；`QFbScreen` 创建同格式的合成图像；`QLinuxFbScreen` 在 `doRedraw()` 中把 touched rect 从合成图像写入 Framebuffer。若 LinuxFB 报告 16 bpp RGB565，则应用侧 RGB16 方向是匹配的，但应用图像仍要经过 backing store 和屏幕合成图像两次搬移。

因此，当前可以表述为“应用内部与 Framebuffer 颜色格式方向一致，未观察到需要 32→16 转换的源码依据”，但不能表述为“整条链路零拷贝”或“直接写入 Framebuffer”。实际格式和拷贝次数仍应在目标板通过 `fbset -i`、Qt QPA 日志和性能测试确认。

## 7. 可优化问题清单

### R1：QImage 被隐式共享后再次写入，触发 detach

这是当前最明确、置信度最高的缺陷。

`SpectrumPlotWidget::workerLoop()` 中执行：

```cpp
frontImage_ = localBackBuffer;
```

该赋值是 Qt 隐式共享浅拷贝，两个 `QImage` 指向同一像素数据。下一轮渲染调用 `renderToImage(ctx, localBackBuffer)` 时，`targetImage.bits()` 会发现数据仍被 `frontImage_` 共享，从而触发写时复制：

- 重新分配一幅图像；
- 复制旧像素；
- 随后又被 `staticLayer_` 的整幅内容覆盖。

在 2K 全屏场景下，这可能意味着每帧额外的数 MiB 堆分配和无效复制。历史板端记录曾把该问题估计为约 20 ms 级开销，但该数字只能作为复测线索，不能直接作为当前版本结论。

### R2：每帧复制整个控件静态层

`renderToImage()` 当前无条件执行：

```cpp
std::memcpy(targetImage.bits(), staticLayer_.constBits(), staticLayer_.sizeInBytes());
```

无论控制器边界、坐标轴和标题是否变化，也无论这些区域是否被本次 `paintEvent()` 更新，每帧都复制整个控件大小的图像。动态内容真正只位于 `plotRect_` 内，因此可以只恢复绘图区静态背景。

### R3：2K 宽度折线的通用 QPainter 光栅化仍有成本

当前折线点数约为绘图区宽度。2K 全屏时可能达到约 2000～2400 个顶点，每个显示帧都要通过通用 `QPainter::drawPolyline()` 进行裁剪、坐标转换和软件光栅化。Marker 数量很少，不是主要成本；折线和整图复制更值得先测量。

### R4：后台离屏路径没有被证明优于同步直绘

单后台线程的价值是解除 GUI 线程阻塞，但它也会引入：

- 完整离屏渲染；
- 前后缓冲同步；
- 额外的内存流量；
- GUI 再贴图；
- LinuxFB backing store 与 screen image 合成。

历史板端记录中曾出现“后台线程约 48 ms/帧、同步 RGB16 约 5 ms/帧”的对照线索。该数据来自旧版本和旧场景，不能直接外推，但足以否定“离屏一定更快”的假设。当前实现同时保留同步兜底，却没有正式的运行模式选择和前后对照统计，因此无法判断当前板端哪条路径更优。

### R5：瀑布图在 GUI 线程完成大部分重复工作

与频谱不同，瀑布图的降采样、颜色索引映射、历史图缩放和静态装饰都在 GUI 线程执行。只要瀑布图可见，它就会与频谱的 GUI 贴图竞争同一个事件循环。

### R6：10 ms 定时器不等于屏幕刷新率

`MainWindow` 每 10 ms 尝试读取一次新帧，但屏幕可能运行在 30、60 或其他刷新率，LinuxFB 也不保证 VSync。结果是：

- 渲染完成快时会执行大量无意义的状态检查和上下文覆盖；
- 渲染完成慢时仍会不断提交新上下文；
- 没有明确的 30/60 FPS 运行档位；
- 无法判断“实际显示能力”和“定时器尝试频率”的差异。

### R7：显示链路存在多级图像复制

即使应用侧做到完美，Qt LinuxFB 仍会把窗口图像合成到屏幕图像，再写入 mmap Framebuffer。若测量显示应用侧耗时很低，但总帧率仍被限制在某个值，下一步应检查这条 QPA 路径，而不是继续增加应用线程。

### R8：应用图像格式为固定 RGB16

历史板端是 RGB565，因此固定 RGB16 是合理的。若未来更换的 Framebuffer 或 QPA 是 RGB32/ARGB32，应用仍生成 RGB16，可能在 backing store 或合成阶段发生格式转换。建议后续增加 `auto / rgb16 / rgb32` 配置，但板端默认仍应保持已验证的 RGB16。

### R9：现有指标不能定位完整瓶颈

`lastPaintMilliseconds()` 只统计一次 GUI `paintEvent()`，不包含：

- 后台线程实际渲染耗时；
- 静态层复制耗时；
- 折线光栅化耗时；
- 瀑布图 `addFrame()` 耗时；
- Qt backing store 和 QPA 合成耗时；
- 扫描输出完成时间。

`framePainted` 在 `paintEvent()` 内发出，只能说明 Qt 完成了本次绘制调用，不能严格说明像素已经出现在显示器上。现有 P95 指标应改称“Qt 绘制完成延迟”，除非另外增加外部可见性测量。

## 8. 方案比较

| 编号 | 方案 | 主要收益 | 风险 | 是否需要板端验证 | 建议优先级 |
|---|---|---|---|---|---|
| S0 | 增加渲染分段计时和基准模式 | 先确定真实瓶颈 | 低 | 是 | P0 |
| S1 | QImage Ping-Pong 双缓冲 | 消除 COW 分配和复制 | 低 | 是 | P0 |
| S2 | 只恢复绘图区静态背景 | 减少每帧静态层复制 | 低 | 是 | P1 |
| S3 | 瀑布图静态层缓存 | 去掉重复文字、网格和色条创建 | 低 | 是 | P1 |
| S4 | 预量化 RGB16 瀑布历史缓存 | 去掉逐帧调色板转换 | 中 | 是 | P1/P2 |
| S5 | `direct / offscreen` 运行模式 | 用数据选择最优路径 | 低/中 | 是 | P1 |
| S6 | 可配置 30/60/100 FPS 显示上限 | 减少无效刷新和 CPU 占用 | 低 | 是 | P1 |
| S7 | RGB565 像素列直接光栅化 | 降低折线通用绘制开销 | 中 | 是 | P2 |
| S8 | 局部恢复旧轨迹脏区 | 减少动态区域清屏量 | 中 | 是 | P2，条件实施 |
| S9 | DRM/KMS page flip 或自定义 Framebuffer 后端 | 可能绕过多级 Qt 合成复制 | 高 | 是 | P3 |
| S10 | PL/DPDMA 图层或 B/S 远程渲染 | 可从根本上转移板端绘制负载 | 很高 | 是 | P4 |

“优先级高”表示应当先验证或实施，不表示一定能带来固定百分比提升。

## 9. 具体优化方案

### S0：建立板端基线测量

#### 目标

在修改性能路径前，先获得同一版本、同一场景、同一屏幕参数下的可重复基线。没有基线时，不应把任何 FPS 变化归因于某一项优化。

#### 建议增加的指标

| 指标 | 说明 |
|---|---|
| `renderTotalMs` | 后台单帧 `renderToImage()` 总耗时 |
| `geometryMs` | 包络压缩和折线顶点构建耗时 |
| `staticRestoreMs` | 每帧静态层复制耗时 |
| `traceMs` | 折线和 Marker 绘制耗时 |
| `guiBlitMs` | GUI `paintEvent()` 贴图耗时 |
| `waterfallIngestMs` | `addFrame()` 降采样和颜色映射耗时 |
| `waterfallPaintMs` | 瀑布图单次 `paintEvent()` 耗时 |
| `pendingOverwriteCount` | 新上下文覆盖未开始上下文的次数 |
| `syncFallbackCount` | 离屏图不可用而走同步绘制的次数 |
| `qtPaintLatencyMs` | 从发布时间戳到 `framePainted` 的延迟，明确不是物理屏幕延迟 |
| `displayFps` | 实际进入 `framePainted` 的显示更新率 |

建议用固定长度环形窗口统计 P50、P95 和 P99，并定期输出到日志。不要只显示最后一次采样值。

#### 建议增加的诊断模式

新增仅用于测试的启动参数或配置项：

```text
--render-mode direct|offscreen
--display-fps 30|60|100
--render-benchmark static|trace|waterfall|mixed
--render-diagnostics
```

其中 `static` 模式反复显示一张已完成静态图，用于测出 GUI 贴图、Qt backing store 和 LinuxFB 提交的显示上限；`trace` 模式只增加折线，用于判断光栅化成本；`mixed` 同时打开频谱和瀑布图。

### S1：真正的 Ping-Pong 双缓冲

#### 当前问题

`frontImage_ = localBackBuffer` 之后继续写 `localBackBuffer`，会触发 QImage 写时复制。

#### 建议实现

后台线程保留两幅同尺寸 RGB16 工作图，发布时在 `frontImageMutex_` 保护下交换：

```cpp
{
    std::lock_guard<std::mutex> lock(frontImageMutex_);
    frontImage_.swap(localBackBuffer);
    hasFrontImage_ = true;
}
```

交换后，`localBackBuffer` 持有上一帧图像，下一轮可以安全覆盖；`frontImage_` 持有刚完成的新图像。GUI 读取 `frontImage_` 时仍使用同一把锁，保持现有线程安全边界。

#### 需要验证

- 首帧、窗口缩放、主题切换时两幅缓冲尺寸是否一致；
- 交换后 `localBackBuffer` 是否确实不再被 GUI 共享；
- 高分辨率下内存峰值是否可接受；
- 同步兜底路径不会与后台发布同时写同一幅图。

#### 预期

消除每帧 QImage `detach()` 造成的重新分配和复制，属于低风险、高置信度的改进。具体收益需在 2K 板端测量。

### S2：每帧只复制绘图区静态背景

#### 设计方案

保持 `frontImage_` 与控件同尺寸，保证 `paintEvent()` 可以按任意脏矩形贴图，但每帧只把 `plotRect_` 区域从 `staticLayer_` 复制到目标图：

```text
if 静态层刚重建 或 目标图刚分配:
    targetImage = staticLayer_.copy()
else:
    for y in plotRect_.top() .. plotRect_.bottom():
        memcpy(
            targetImage.scanLine(y) + plotRect_.left() * 2,
            staticLayer_.constScanLine(y) + plotRect_.left() * 2,
            plotRect_.width() * 2
        )
drawTraceAndMarkers()
```

静态层重建、控件尺寸变化、主题变化、幅度范围变化时仍执行全图初始化。其余帧只恢复绘图区，因为坐标轴、标题和边距内容不会变化。

#### 更激进的次级方案

如果静态背景复制仍占主要时间，可记录上一帧折线和 Marker 实际覆盖的矩形，只恢复这些区域。但频谱噪声可能让轨迹分布在整个绘图区，回退收益有限，必须在 S0 数据支持下再做。

#### 风险

- 必须防止旧轨迹在 Marker 或折线区域留下残影；
- 静态层与目标图的行跨度可能不同，不能假设整块内存连续；
- 不同像素格式下字节宽度不同，当前仅对 RGB16 使用 `×2`。

### S3：瀑布图静态层缓存

#### 缓存内容

新增一个与瀑布控件同尺寸的 RGB16 静态层，包含：

- 控件背景；
- 绘图区背景；
- 频率轴和时间轴文字；
- 色标文字；
- 色条图像；
- 标题和单位。

网格和边框只有十余条线，可以每帧直接绘制，或在不发生混合开销的前提下并入静态层。这样既保留网格覆盖数据的层级关系，又避免每帧重建文字和色条。

#### 失效条件

静态层只在以下情况重建：

- 控件尺寸变化；
- 亮/暗主题变化；
- 幅度范围变化；
- 频率范围变化；
- 历史深度或轴标签策略变化。

`paintEvent()` 应使用 `event->rect()` 作为裁剪和静态层绘制范围，不再无条件填充整个控件。

#### 色条优化

`1×256` 的色条图像应与调色板一起缓存，而不是每次 `paintEvent()` 重新创建和逐像素 `setPixel()`。切换色表时重建一次即可。

### S4：预量化 RGB16 瀑布历史缓存

#### 设计方案

保留 `Indexed8` 作为历史源数据，同时增加相同宽高的 `rgbBufferImage_`：

```text
bufferImage_    : Format_Indexed8，保留色号历史
rgbBufferImage_ : Format_RGB16，保留已展开的 RGB565 历史
```

`addFrame()` 写完索引行后，立即把该行索引通过调色板转换为 RGB565，并写入 `rgbBufferImage_` 对应行。`drawWaterfallImage()` 直接绘制 RGB16 缓存。

切换色表或幅度范围时，从 `bufferImage_` 重建一次 RGB16 缓存。这个操作只发生在用户交互，不是每帧执行。

#### 收益

- 去掉每次 `paintEvent()` 的逐像素调色板展开；
- 源图与 LinuxFB 常用的 RGB16 目标格式一致；
- 仍保留索引色源数据，色表切换不需要重采历史频点。

#### 代价与风险

- 历史缓存内存从每像素 1 字节增加到约 2 字节；
- 例如 `2000×512` 的索引历史和 RGB16 缓存合计约 `3 MiB`；
- `2000×2048` 时 RGB16 缓存约 `8 MiB`；
- 目标板可用内存不足时应改用“只缓存可见窗口高度”的方案；
- 需要验证全屏切换、历史深度调整和色表切换时的重建正确性。

如果 S0 显示瀑布图 `paintEvent()` 并非主要瓶颈，则本项可推迟。

### S5：增加 `direct / offscreen` 渲染模式

#### 设计

在 `SpectrumPlotWidget` 中抽象一个明确的渲染模式：

```text
direct    : paintEvent() 在 GUI 线程直接调用 RasterSpectrumRenderer::paint()
offscreen : 使用当前单后台线程和 Ping-Pong 成品图
auto      : 初期保留，但只有取得 A/B 数据后再定义切换策略
```

第一轮建议只实现并验证 `direct` 与 `offscreen`。不要在没有数据时设计复杂的自动切换状态机。

#### 测试方式

同一目标板、同一屏幕、同一频点数、同一输入帧率、同一主题和同一视图模式下，分别运行：

```text
direct + 2K
offscreen + 2K
direct + 1080p
offscreen + 1080p
```

记录渲染总耗时、GUI 耗时、显示 FPS、P95 延迟、每核 CPU 和同步兜底次数。

#### 可能的结论

- 若 `direct` 的 GUI 单次绘制低于 16.6 ms，且没有阻塞交互，应优先使用 `direct`，因为它少一层离屏发布和等待；
- 若 `offscreen` 的总吞吐更高但 GUI 更流畅，可保留离屏并优化缓冲复制；
- 若两者都不足，瓶颈可能在 LinuxFB 合成，而不是应用绘制。

### S6：可配置显示刷新上限

#### 设计方案

将当前固定的 10 ms 定时器改为可配置周期，并明确区分：

```text
输入/发布帧率
目标显示刷新率
实际完成绘制帧率
屏幕刷新率
```

首轮建议提供 30、60、100 FPS 三档，默认值保持当前行为或由板端基线决定。不要把 60 FPS 写成无条件保证。

如果渲染任务尚未完成，新的显示 tick 只更新“最新待渲染帧”，不能建立无限队列。现有 `LatestFrameStore` 和 `pendingContext_` 的覆盖策略应保留。

#### 进一步优化

只有在目标板确认 LinuxFB 与 VSync 关系后，才考虑：

- 以屏幕刷新周期为基准调度；
- 在无 VSync 时使用固定 30 FPS 优先保证稳定；
- 使用外部帧完成信号而不是固定定时器。

### S7：RGB565 像素列直接光栅化

#### 适用条件

只有在 S0 证明 `traceMs` 中 QPainter 折线绘制占显著比例，且 Marker 文字不是主要成本时，才实施。

#### 设计

对 `traceWidth == 1` 的默认轨迹：

1. 从已完成包络中取得每个屏幕列的主轨迹 `(x, y)`；
2. 直接把轨迹写成目标 `QImage::Format_RGB16` 的 RGB565 像素；
3. 对相邻列之间绘制竖直连接，避免折线断裂；
4. Marker、三角和文字继续使用 `QPainter`；
5. 若用户选择 2～4 像素线宽，暂时回退到 `QPainter::drawPolyline()`。

#### 注意

- 必须正确完成 `QColor -> RGB565` 量化；
- 必须保持裁剪到 `plotRect_`；
- 必须避免直接写像素与 QPainter 同时操作同一图像；
- 必须用截图对比验证峰值位置、线宽和颜色；
- 不能因为直接写像素而丢失窄峰或改变 Marker 的 bin 对应关系。

### S8：局部恢复旧轨迹

这是一项条件优化。实现时应记录上一帧折线和 Marker 的包围矩形，只从静态层恢复这些区域，再绘制新轨迹。

如果频谱噪声使轨迹覆盖几乎所有绘图区，局部恢复的收益会显著下降。该方案只有在 S0 证明“静态背景恢复”仍是主要耗时，且轨迹区域明显小于整个绘图区时才值得采用。

### S9：评估更直接的显示后端

#### 前提

先在板端确认：

- `QT_QPA_PLATFORM` 实际值；
- `fbset -i`、`/sys/class/graphics/fb0/*`；
- `/dev/dri/card*`、`/dev/dri/renderD*` 是否存在；
- Qt 5.15 是否提供可用的 KMS/DRM 相关插件；
- Framebuffer 是否支持双缓冲或 `FBIOPAN_DISPLAY`；
- 显示控制器是否在 VSync 中断后完成 page flip。

只看到 `/dev/fb0` 或 `/dev/dri/card0` 不能证明存在 GPU。DRM 设备也可能只是显示控制器。

#### 候选路线

| 路线 | 机制 | 预期收益 | 风险 |
|---|---|---|---|
| 继续 LinuxFB + 局部更新 | 减少 Qt 合成区域 | 低风险、可渐进 | 不能消除 backing store 和 screen image 复制 |
| DRM/KMS dumb buffer + page flip | CPU 绘制到两张 RGB565 dumb buffer，按 VSync 切换 | 可能减少一次合成并降低撕裂 | 需要 DRM master、驱动和 Qt 集成验证 |
| Framebuffer panning 双缓冲 | 利用虚拟高度和 `FBIOPAN_DISPLAY` | 可能减少屏幕写入和撕裂 | 依赖驱动支持，缺少同步保证 |
| 自定义全屏 Framebuffer 后端 | 应用直接管理 mmap、双缓冲和提交 | 可控性最高 | 工程量和兼容风险最高 |

这些路线只应在低风险应用层优化完成后进行独立原型。原型应先在独立测试程序或专门的全屏测试窗口中验证，不应直接改坏主程序。

### S10：PL/DPDMA 图层和远程渲染

#### PL/DPDMA 图层

如果显示控制器支持多图层或独立扫描输出，可以把频谱动态图作为单独图层，由 PL/显示硬件直接读取，从而减少 PS 对整幅 UI 的反复合成。该方案需要：

- 显示控制器和 DPDMA 的明确能力证据；
- 图层格式、内存布局、同步和地址配置；
- 与 Qt UI 的坐标和层级协调；
- 独立的故障恢复方案。

这是长期架构候选，不适合作为本轮第一步。

#### B/S 远程渲染

板端只负责采集、处理和发送频谱数据，PC 或浏览器负责渲染。该方案可以显著降低板端显示负担，但会改变当前“板端独立显示仪器”的产品形态，并引入网络延迟、带宽、断线恢复和安全问题。除非产品形态允许，否则只作为备选。

## 10. 明确不推荐的做法

1. **重新采用 OpenGL ES2/EGLFS**：当前目标平台没有可用 GPU，软件 GL 不会提供预期加速。
2. **直接创建多个渲染 worker**：单幅 QPainter 图像难以自然并行，多个线程会争用同一内存带宽和锁。
3. **第一步就给线程绑核**：没有测量证据时，绑核可能降低调度弹性，甚至与 DMA/中断处理争核。
4. **固定把折线降到 512 点**：当前不是固定 512 点；强制降采样可能损害窄峰显示和视觉一致性。
5. **无条件追求 60 FPS**：应先把 30 FPS 作为必须达成的底线，再根据屏幕和板端数据决定 60 FPS 的范围。
6. **把 `framePainted` 当成物理屏幕显示完成**：该信号发生在 Qt 绘制路径内，不能替代外部可见性测量。
7. **在没有 VRAM/Framebuffer 设计前直接写 `/dev/fb0`**：缺少双缓冲和同步时会引入撕裂、竞态和恢复问题。

## 11. 推荐实施顺序

### 阶段 A：低风险、可独立回退

1. S0：增加分段计时、P50/P95/P99、覆盖计数和静态/动态基准模式；
2. S1：Ping-Pong 双缓冲；
3. S2：只恢复绘图区静态背景；
4. S3：瀑布图静态层和色条缓存；
5. S5：`direct / offscreen` A/B 模式；
6. S6：30/60/100 FPS 显示上限。

阶段 A 不改变峰值搜索、Marker 坐标、频谱数据或显示后的 bin 映射，只改变绘制和调度路径。

### 阶段 B：依据阶段 A 数据决定

1. 如果瀑布图是 GUI 瓶颈，实施 S4；
2. 如果折线光栅化是主要耗时，实施 S7；
3. 如果轨迹脏区明显小于绘图区，实施 S8；
4. 如果 GUI 单次绘制和后台总渲染都低、但显示帧率仍受限，转入 S9 的显示后端原型。

### 阶段 C：架构级方案

只有阶段 A、B 仍不能满足硬件平台目标时，才评估 DRM/KMS/Framebuffer 自定义后端、PL/DPDMA 图层或 B/S 分离。

7. 所有结论都附带同一版本的测试命令、原始日志和前后对照。

## 13. 风险与回退

| 风险 | 控制方式 |
|---|---|
| Ping-Pong 交换导致首帧或 resize 花屏 | 保留同步兜底；尺寸变化时使双缓冲失效并重建 |
| 局部背景复制留下旧轨迹 | 先实现全绘图区恢复，再考虑 S8；截图对比和残影测试 |
| 瀑布图 RGB16 缓存内存过高 | 保留 Indexed8 源数据；可限制历史深度或只缓存可见窗口 |
| 直绘模式阻塞 UI | 保留 offscreen 模式；通过运行参数切换 |
| 显示上限降低观感 | 默认保持当前行为，验证后再改变默认值 |
| 自定义 Framebuffer 后端崩溃或死锁 | 独立原型，不直接替换主路径；保留 LinuxFB 启动选项 |
| 分辨率变化导致性能不达标 | 将分辨率纳入验收矩阵；记录屏幕和控件实际尺寸 |

所有性能优化都应以独立提交或至少独立 diff 保存，以便出现视觉回归时单独回退；不得通过回退用户已有的 UI 兼容性修改来处理渲染问题。
