# 渲染与显示详解 —— 无 GPU 的实时频谱绘制

> 对应任务分解里的 G 模块。本文按"难在哪 → 先懂哪些概念 → 链路全景 → 频谱图怎么画 → 瀑布图怎么画 → 性能从哪来 → 已知边界 → 怎么验证 → 从零实现的顺序"展开。
> 所有描述都对应当前仓库的 `src/plot/` 与 `src/core/EnvelopeReducer.*`，不是泛泛的图形学教程。

---

## 0. 这件事到底难在哪

一句话：**要画的点比屏幕上的像素多得多，而且每秒要重画几十次，还没有显卡帮忙。**

算笔账。一帧 65536 个频点，屏幕绘图区宽 1800 像素。如果把 65536 个点都交给绘图库去画，等于每个像素上要落 36 个点，绝大部分计算是白费的——因为它们最终都画在同一个像素上。再乘以每秒 1000 帧的输入，就是每秒 6500 万个点。

更麻烦的是目标平台没有 GPU。ZU47DR 常见的配置里没有 Mali 之类的图形核，程序只能靠 CPU 一个像素一个像素地画。而这块 CPU 还要同时应付 DMA 取数、数据转换、协议解析。

所以这个模块的全部工作可以概括成三句话：

1. **减少要画的点**——用包络降采样，把 N 个频点压成屏幕宽度的数量级。
2. **减少要画的次数**——不变的内容画一次存起来，只重画变化的部分。
3. **减少主线程的负担**——把重的绘制搬到后台线程，主线程只做轻量的"贴图"。

这三条就是整个渲染架构的设计主线，后面的每一段代码都是在落实它们。

## 1. 动手前要懂的六个概念

**光栅化**：把"画一条线"这种指令，变成"哪些像素该点亮、什么颜色"的过程。Qt 的 `QPainter` 画在 `QImage` 上时就是软件光栅化，纯 CPU 计算，不涉及显卡。

**离屏渲染**：不直接往屏幕上画，而是先画到内存里的一张图片上，画完再一次性贴到屏幕。好处是可以放到别的线程去做。

**双缓冲**：后台线程往"后缓冲"画，画完切换给主线程当"前缓冲"用。这样主线程永远看到一张完整的图，不会看到画到一半的样子。

**脏区重绘**：屏幕上没变的地方不需要重画。Qt 在 `paintEvent` 里会告诉你"这次要重画哪块矩形"，只贴这一块就行，而不是整个窗口重来一遍。

**包络降采样**：把一段连续的频点合并成一个像素列时，不是随便取一个点，而是保留这一段里的**最小值和最大值**。这样即使某个窄峰只占一个频点，它所在的那一列也会因为"最大值很高"而被画出来，不会凭空消失。

**索引色（Indexed8）**：每个像素只存一个 0~255 的编号，真正的颜色查一张 256 项的调色板。相比每像素 4 字节的常规格式，内存直接省到四分之一。瀑布图用它，因为它要保存几百行历史。

## 2. 显示链路全景

```
  采集线程                                    主线程
┌──────────────┐                        ┌──────────────────┐
│ 新频谱帧      │                        │ 10ms 定时器       │
└──────┬───────┘                        │ 读最新帧          │
       │ FrameSink                       └────────┬─────────┘
       ▼                                          ▼
┌──────────────┐                        ┌──────────────────┐
│ SpectrumPipeline（校验+轨迹）            │ setFrame()       │
└──────┬───────┘                        └────────┬─────────┘
       ▼                                          ▼
┌──────────────┐   打包 RenderContext   ┌──────────────────┐
│ LatestFrameStore（原子最新帧）          │ pendingContext_  │
└──────┬───────┘ ─────────────────────► │ （只保留最新一个）│
       │                                └────────┬─────────┘
       │ 主线程读取                              │ 唤醒
       │                                         ▼
       │                                ┌──────────────────┐
       │                                │ 离屏渲染线程      │
       │                                │ renderToImage()  │
       │                                └────────┬─────────┘
       │                                         ▼
       │                                ┌──────────────────┐
       └───────────────────────────────►│ frontImage_      │
                                        │ （RGB16 成品图）  │
                                        └────────┬─────────┘
                                                 ▼
                                        ┌──────────────────┐
                                        │ paintEvent()     │
                                        │ 只贴脏区         │
                                        └──────────────────┘
```

关键点：**主线程不画图，只贴图。** 所有的几何计算和曲线栅格化都在那个离屏线程里完成。主线程每次只做一次"把某个矩形区域从内存图片拷到窗口"的操作。

## 3. 频谱图的分层结构

画一张频谱图，内容可以分成三类，变化频率完全不同：

| 内容 | 变化频率 | 处理方式 |
|---|---|---|
| 背景、网格、坐标轴、刻度文字、边框 | 几乎不变（只在窗口尺寸/量程/主题变化时变） | 画一次，缓存成图片 |
| 频谱曲线 | 每帧都变 | 每帧重画 |
| Marker 标记 | 用户操作时变 | 每帧重画（很轻） |

这三层对应代码里的三个部分：`staticLayer_`（静态层图片）、`peakPolyline_`（曲线点集）、`markerBins_`（标记位置）。

为什么要这样分？因为**画文字和网格其实很贵**。`drawText` 每次都要做字体光栅化，一个刻度标签可能就要几十微秒。如果每帧都重画十几个标签，光这一项就能吃掉好几毫秒。缓存成图片之后，这些开销从"每帧"降到"只在变化时"。

---

## 4. 静态层：把不变的东西画一次

`rebuildStaticLayer()` 负责生成这张缓存图片，步骤如下：

1. **建一张和控件同尺寸的 RGB16 图片**。选 16 位色是因为它比 32 位省一半内存带宽，而频谱图这种渐变不多的画面，16 位色完全够看。
2. **按主题选颜色**。代码里有五种主题：经典深黑、明亮浅色、深海科技、复古纯黑、自定义背景色。自定义主题还会根据背景的明暗自动推算网格色、边框色和文字色，避免出现"浅色背景配白字"看不清的情况。
3. **填背景、填绘图区**。
4. **画网格**：横竖各 10 等分。网格可以开关。
5. **画边框**。
6. **画幅度刻度**：纵轴 10 等分，右侧对齐，数值由参考电平和底部电平线性插值得到。
7. **画频率刻度**：横轴每隔 2 格标一个，格式自动选 GHz/MHz/kHz/Hz。标签会做边界钳制，防止最右边那个标签被截断。
8. **画中心频率与带宽标题**，以及旋转 90 度的纵轴单位文字。

这张图片只有在三种情况下会重建：窗口尺寸变了、量程（参考电平/底部电平）变了、主题或外观变了。`staticLayerDirty_` 这个标志位就是干这个的。

## 5. 包络降采样：6 万个点怎么塞进 2000 像素

这是整个渲染里最核心的一步，实现在 `EnvelopeReducer::reduce()`。

做法是按屏幕像素列把频点分段。假设有 `N` 个频点、`W` 个像素列：

```
第 c 列覆盖的频点范围：
  begin = c × N / W
  end   = (c+1) × N / W     （至少包含一个点，且不超过 N）
```

然后对这一段的每个点做两件事：跳过非有限值（NaN/Inf），记录这段里的最小值 `minimum` 和最大值 `maximum`，同时记下这段的起止频点号 `firstBin`/`lastBin`，最后打一个 `valid` 标记（整段都没有有效值时为 false）。

输出是一个 `EnvelopeColumn` 数组，长度等于像素列数。**无论输入是 1024 点还是 65536 点，输出长度都只跟屏幕宽度有关**，这就是"绘制点数与屏幕同阶"的由来。

有一点要如实说明：**当前代码只把每列的 `maximum` 连成折线画出来，`minimum` 虽然算出来了，但没有画成垂线。**

```
现在画的：      每列取最大值 → 连成折线
理想效果：      每列画一条从 min 到 max 的竖线 → 形成"填充包络"
```

这是已知的未完成项。对显示效果的影响是：噪声底看起来会比实际平滑，因为只显示了每列的上边界。对测量**没有**影响——Marker、峰值搜索和 CSV 导出都直接用完整频点，不走这条降采样路径。

## 6. 离屏渲染线程：为什么要有，怎么避免积压

`SpectrumPlotWidget` 在构造时启动一个后台线程，跑 `workerLoop()`。它的工作方式很特别：

```
workerLoop 循环：
  1. 等条件变量（没有任务就睡）
  2. 醒来后把 pendingContext_ 搬走，清掉标志
  3. 调用 renderToImage 渲染整幅图
  4. 把结果放进 frontImage_（加锁）
  5. 用队列连接通知主线程重绘
```

关键在于 **`pendingContext_` 只有一个**。主线程 `setFrame()` 时不排队，而是直接覆盖它：

```
主线程 setFrame()：
  加锁 → pendingContext_ = 新上下文 → 置标志 → 解锁 → 通知线程
```

这带来一个很重要的性质：**如果渲染速度跟不上输入帧率，中间那些帧会被直接丢掉，而不是排队等**。输入 1000 帧/秒、渲染只能做 35 帧/秒时，缓冲区里永远只有"最新那一帧"，不会越积越多导致延迟无限增长。

这个策略叫"最新任务覆盖"。它的代价是显示上会跳过一些帧（统计里有"显示跳过帧"这个计数），换来的是延迟稳定、内存不涨。对频谱仪这种"看当前状态"的应用，这个取舍是对的。

线程退出时，析构函数先置 `workerStopping_` 再 `notify_all`，最后 `join`，保证不会留下野线程。

## 7. 主线程的 paintEvent：只贴脏区

主线程的绘制逻辑非常短，就三件事：

```
paintEvent(event):
  1. 从事件里取出要重画的矩形 dirty（空则整窗）
  2. 如果 frontImage_ 就绪且尺寸匹配：
         painter.drawImage(dirty.topLeft(), frontImage_, dirty)
     —— 只把这一块切片贴上去
  3. 否则：同步调用 renderer_.paint(painter) 兜底
```

第 2 步那句 `drawImage(dirty.topLeft(), frontImage_, dirty)` 是整个优化的落点：1080p 全屏是 200 多万像素，如果每帧整屏拷贝，光是内存搬运就是几毫秒。只贴脏区之后，这个开销大幅下降。

第 3 步的"兜底"也必须存在，而且不能省。有三种情况会走到这里：

- 程序刚启动，后台线程还没渲染出第一张图；
- 窗口尺寸刚变过，旧图尺寸不匹配；
- 单元测试里同步调用绘制。

没有这条兜底路径，冷启动或窗口刚出现时会出现空白。同时它也是为什么不能宣称"所有帧永远异步完成"的原因——同步路径确实存在，只是正常情况下不走。

`paintEvent` 末尾会记录本次耗时（`lastPaintMilliseconds_`）和是否走了离屏路径（`isLastPaintOffscreen_`），并发出 `framePainted` 信号。这三个数据是后面统计显示延迟 P95 的输入。

窗口尺寸变化时，`resizeEvent` 会把 `hasFrontImage_` 置 false，强制下一帧走重新渲染。

## 8. 曲线与 Marker 怎么画

`drawTraceAndMarkers()` 在离屏线程里执行，做两件事。

**画曲线**：把 `peakPolyline_`（每列最大值的坐标点）用 `drawPolyline` 一次画完。注意它把抗锯齿关掉了（`setAntialiasing(false)`）——抗锯齿会让每个像素做混合运算，对一条实时刷新的曲线来说，性能代价不值得。

**画 Marker**：最多 4 个，颜色是固定的四种（琥珀黄、青蓝、洋红、翠绿）。每个启用的 Marker 画三样东西：

1. **竖直虚线标尺**——只在 Marker 处于激活状态时画，而且只从数据点向下落到 X 轴，不横跨整个屏幕。这样做的目的是不遮挡其他信号。
2. **倒三角标**——锚定在数据点上，激活时实心、非激活时半透明。
3. **编号标签**（M1~M4）——画在三角上方，如果靠近绘图区顶部就自动翻到下方，避免被裁掉；水平方向也做了左右边界钳制。

所有绘制都在 `painter.save()/restore()` 之间，并设置了 `setClipRect(plotRect_)`，保证不会画到坐标轴区域外面去。

## 9. 瀑布图：索引色环形缓冲

瀑布图记录的是"频谱随时间变化"的历史，横轴是频率、纵轴是时间。它的问题是**要保存很多行历史**（默认 512 行，最多 2048 行），如果每行都用常规 32 位色存，内存会很大。

所以它用了索引色：每个像素只存一个 0~255 的色号，真正的颜色查调色板。

```
1920 列 × 512 行  索引色：约 0.94 MB
1920 列 × 512 行  32 位色：约 3.75 MB
```

数据结构是一个环形缓冲：

```
bufferImage_   索引色图片，宽 = 绘图区宽度，高 = 历史深度
headRow_       最新一行在物理图片里的行号
rowCount_      已写入行数（最大等于历史深度）
historyDepth_  历史深度（64~2048）
colorTable_    256 项调色板
```

每来一帧，`addFrame()` 做四步：

1. **按列取最大值**，把 N 个频点压成绘图区宽度个数值（这一步和频谱图的包络降采样是同一个思路，但只取最大值，因为瀑布图要的是"这一列最强信号"）。
2. **头指针向前移一格**：`headRow_ = (headRow_ - 1 + historyDepth_) % historyDepth_`。往前移而不是往后移，是为了让"最新的一行"出现在屏幕最上方，符合直觉。
3. **把这一行的色号写进去**：每个数值经 `mapToColorIndex` 变成 0~255 的色号，写进对应的扫描线。
4. **只标记瀑布绘图区重绘**，不动其他区域。

稳态运行时**不做整图搬移**——每帧只写一行。这是环形缓冲相对"整体上移"做法的核心优势：历史深度从 512 涨到 2048，单帧写入量几乎不变。

## 10. 瀑布图怎么画：双切片

因为是个环，逻辑上"从上到下"的顺序在物理内存里可能是断开的：

```
物理图片：  [0 ... headRow_-1] 是较旧的数据
           [headRow_ ... 末尾] 是较新的数据

屏幕顺序：  顶部 = 最新 = [headRow_ ... 末尾]
           底部 = 较旧 = [0 ... headRow_-1]
```

所以绘制时要把一张图拆成两个矩形分别贴：

```
如果历史还没填满（rowCount_ < historyDepth_）：
    只贴一段：源 [headRow_, rowCount_ 行] → 目标顶部一小块

如果已经填满：
    切片 1：[headRow_ ... 末尾] → 屏幕上方
    切片 2：[0 ... headRow_-1] → 屏幕下方
```

这就是"双切片"的含义——**同一张环形图按逻辑顺序拆成两个源矩形**，不是两张独立的图，也不是零拷贝（每帧仍然要做图像缩放和绘制）。

## 11. 三种尺寸变化场景

窗口大小变了，历史图必须重建。`resizeImageBuffer()` 按三种情况分别处理，这个细节挺讲究：

| 情况 | 处理方式 | 为什么 |
|---|---|---|
| 宽度不变 | 逐行 memcpy | 最快，直接搬 |
| 宽度变大（如进全屏） | 双线性插值 | 拉宽时用插值，画面平滑不出现色块 |
| 宽度变小（如退出全屏） | 峰值保持（取区间最大值） | 缩小会丢信息，取最大值能保住窄信号不被"缩没" |

缩小时用峰值保持而不是插值，是这个模块一个值得写进论文的取舍：**插值会让窄峰被平均掉，而频谱仪最不能容忍的就是"信号看不见了"。**

历史行本身按顺序搬到新图片的底部对齐位置，然后更新 `headRow_` 和 `rowCount_`。所以文档里"环形缓冲永不搬移"这个说法只在固定几何下的稳态成立——改窗口尺寸或改历史深度都会触发一次重建。

## 12. 色表与映射

瀑布图的颜色由两步决定。

**第一步：幅度 → 色号（0~255）**，实现在 `Colormap::mapToColorIndex`：

```
非有限值                    → 色号 0
参考电平 ≤ 底部电平          → 退化成二值映射（≥参考电平取 255，否则 0）
正常情况                    → (幅度 - 底部电平) / (参考电平 - 底部电平) × 255，向下取整并钳制
```

注意那句"退化成二值映射"——这是防止参考电平和底部电平相等时除零。这类边界处理不做，就会出现整屏同一颜色的诡异画面。

**第二步：色号 → 实际颜色**，由 256 项调色板决定。代码内置五种：

| 名称 | 风格 |
|---|---|
| Classic Rainbow | 深蓝 → 青 → 绿 → 黄 → 红 → 白，类似 Keysight/Tektronix 的经典 RF 彩虹 |
| Rohde & Schwarz | 深海蓝 → 青绿 → 金黄 → 橙红 → 白，高对比 |
| Ironbow | 黑 → 紫 → 铁红 → 橙 → 黄 → 白，类似热成像 |
| Deep Ocean | 午夜蓝 → 靛蓝 → 海蓝 → 冰青 → 白 |
| Grayscale | 灰度 |

调色板由若干"颜色停靠点"（位置 + RGB）线性插值生成 256 级。切换色表时只需要调 `QImage::setColorTable()`，**历史像素完全不用重写**——因为像素存的是色号，不是颜色。这是索引色的第二个好处。

## 13. 性能从哪里来（四条主线）

把前面所有措施归一下类，性能收益来自四个方向：

1. **降采样**：绘制点数从"频点数"降到"屏幕列数"。65536 点 → 约 1800 个点，减少约 36 倍。
2. **静态缓存**：网格、坐标、文字只在变化时重画，从"每帧"变成"偶尔"。
3. **离屏 + 脏区**：重的栅格化在后台线程做，主线程只贴变化区域，避免 1080p 全屏内存搬运。
4. **最新任务覆盖**：渲染跟不上时丢弃中间帧，保证延迟稳定、内存不涨。

另外还有几个小优化值得一提：离屏渲染复用同一个目标 `QImage` 缓冲区（尺寸格式匹配时用 memcpy 而不是重新分配），避免每帧几 MB 的堆分配；`peakPolyline_` 预分配容量；渲染线程里对 `frontImage_` 的赋值利用 Qt 的隐式共享做浅拷贝。

**当前 PC 上的实测结果**：16384 点、1000 帧/秒输入、1920×1080 窗口，显示约 33.7 FPS，显示延迟 P95 约 16.5 ms。这个成绩满足"不低于 30 FPS"的底线要求，但没达到"60 FPS"的目标值。

## 14. 已知边界与未完成项

诚实清单，可直接用作论文的"不足与改进"：

1. **最小/最大垂线包络没有绘制。** 最小值算出来了但没用上，目前只画最大值折线。想要"填充包络"的视觉效果需要补这一步。
2. **只有一个离屏渲染线程，没有 CPU 亲和性绑定。** 源码注释里出现过"CPU0/1/2 多核异步"的说法，那是历史残留，不是实现事实。实际调度完全交给操作系统。
3. **板端帧率未验证。** 33.7 FPS 是 PC 数据，不能外推到 ZU47DR。
4. **静态层每帧仍要整体复制一次**到目标图。可以考虑只维护绘图区的静态背景、或按脏区恢复背景来进一步减少。
5. **目标图尺寸跟随整个控件**，而不是只跟绘图区，非绘图区的复制其实是浪费。
6. **RGB16 只是应用内部格式。** 源码能证明应用里用的是 16 位图，但不能证明 Qt 的 backing store、linuxfb 插件或最终写入 framebuffer 的过程中没有再做一次转换——这个必须在板端实测（可以用 `QT_LOGGING_RULES="qt.qpa.*=true"`、`fbset` 和必要的 strace 来看）。
7. **瀑布图的时间轴标签按帧偏移而不是真实秒数**，隐含依赖帧率稳定。如果输入帧率波动，时间轴会不准。

## 15. 怎么验证与调优

**先测量，再优化。** 这个模块已经预留了必要的观测点：

- `lastPaintMilliseconds()`：一次 `paintEvent` 的耗时（只覆盖贴图，不等于渲染线程的耗时）。
- `isLastPaintOffscreen()`：这一帧是走的离屏贴图还是同步兜底。
- `envelopeColumnCount()`：实际生成了多少列包络，用来确认降采样是否生效。
- `framePainted` 信号：带发布时间戳，用来算端到端显示延迟。

**固定测试矩阵**（做前后对比时必须锁死这些变量）：

| 变量 | 建议基线 |
|---|---|
| 数据源 | 模拟源，固定场景 |
| 频点数 | 16384（另测 4096 / 65536） |
| 输入帧率 | 100 / 500 / 1000 FPS |
| 窗口 | 目标板实际全屏尺寸 + 一个固定小窗口 |
| 视图 | 纯频谱 / 纯瀑布 / 双视图 |
| 外观 | 固定颜色、线宽、网格开关 |

**排查顺序**：如果显示慢，先看是渲染线程慢还是主线程贴图慢（用 `isLastPaintOffscreen` 和两个耗时分开看）；再看是不是 Framebuffer/VSync 限制（切换视图对比）；最后才考虑加并发。**在没有数据的情况下就引入线程池或绑核，是在给自己制造问题。**

## 16. 从零实现这个模块，建议的顺序

1. **先做最朴素的同步绘制**：一个 `paintEvent` 里直接画网格、坐标、曲线。先让它动起来。
2. **加包络降采样**：把绘制点数降到屏幕宽度量级，这一步的收益最大。
3. **拆出静态层**：把网格和文字缓存成图片，只在变化时重建。
4. **引入离屏线程 + 双缓冲**：把绘制搬到后台，主线程只贴图。
5. **加最新任务覆盖**：防止渲染积压导致延迟增长。
6. **加脏区贴图**：只更新变化区域。
7. **加同步兜底**：保证冷启动和测试路径不出白屏。
8. **加瀑布图**：索引色环形缓冲 + 双切片绘制。
9. **加色表与切换**：先做彩虹和灰度两个，再补其余。
10. **处理尺寸变化**：同宽复制、放大插值、缩小峰值保持三种情况都要测。
11. **补观测点**：绘制耗时、是否离屏、包络列数、显示延迟，为后续调优留数据。
12. **最后上板实测**：PC 的数字只能当参考，板端 QPA 和 Framebuffer 的实际行为必须实测。
