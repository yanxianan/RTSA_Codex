# 渲染方法调整：由 OpenGL ES2 方案转为无 GPU 的 CPU Raster 方案

## 问题分析

开题阶段拟采用 Qt 框架结合 OpenGL ES2，对实时频谱图像进行硬件加速，并以不低于 30 FPS 作为显示性能目标。然而，随着目标平台确定为 RFSoC ZU47DR 的 PS 端、PetaLinux 2023.2 和 Qt 5.15.x，实际硬件条件表明该开发板不提供可用于通用图形渲染的 GPU，因而也不具备稳定、可依赖的 EGL/OpenGL ES 硬件加速链路。在这种情况下，继续采用 OpenGL ES2 不仅无法获得预期的 GPU 加速效果，还可能因无法创建图形上下文而导致程序启动失败，或者退化为软件 OpenGL 实现，将图形命令处理、纹理上传、颜色转换和缓冲区交换等工作重新转移到 CPU 上，进一步增加系统开销。同时，OpenGL 渲染路径还会引入 GPU 驱动、EGL、Qt 平台插件和显示后端之间更复杂的依赖关系，降低无 GPU 嵌入式环境中的部署可靠性和可移植性。因此，原方案中的 OpenGL ES2 属于开题阶段的技术预设，不能作为最终实现的必要运行前提。

在无 GPU 条件下，实时频谱绘制的主要效率矛盾集中在待绘制频点数量、屏幕分辨率、输入帧率与 CPU 处理能力之间。频谱分析通常需要处理数千至数万个频点，而目标界面又需要在 2K 分辨率下持续刷新频谱曲线、网格、坐标、标记和瀑布图；若每个输入帧都在 GUI 线程中完成全量数据转换和完整窗口重绘，容易造成主线程阻塞、界面响应迟滞和显示帧积压。尤其当输入帧率高于屏幕刷新能力时，如果为每一帧保留绘制任务，队列延迟会不断累积，最终表现为频谱显示落后于实际采集数据。此外，无 GPU 平台上的图像格式转换、整幅图像拷贝和 Framebuffer 提交同样会消耗 CPU 与内存带宽，因此不能简单依赖提高绘制频率来改善实时性，而必须从减少绘制点数、减少无效重绘、降低主线程负载以及丢弃过期显示帧等方面重新设计渲染路径。

## 解决方案

针对上述限制，当前实现放弃 OpenGL ES2 渲染后端，采用基于 Qt Widgets 和 `QPainter` 的 CPU Raster 绘制方案，并将“无 GPU 也能稳定运行”作为基础设计约束。频谱显示首先根据绘图区宽度对完整频点序列进行按屏幕像素列的 min/max 包络压缩，并利用各列最大值形成可见频谱折线，使参与最终绘制的点数由频点总数收敛到屏幕宽度量级，同时避免窄带峰值因简单抽点而丢失。背景、边框、网格、坐标轴和刻度文字等低频变化内容被预先绘制并缓存为 `QImage::Format_RGB16` 静态层，仅在窗口尺寸、坐标范围或显示样式发生变化时重新生成；每帧只更新频谱曲线、Marker 和必要的动态信息。频谱绘制任务由单一后台离屏线程完成，渲染结果写入 RGB16 图像，GUI 线程在 `paintEvent()` 中只将发生变化的脏区贴入窗口，从而把较重的几何计算和像素光栅化移出主线程，并减少全屏图像搬运。

在数据刷新与显示调度方面，数据源发布的完整频谱帧由 `LatestFrameStore` 以原子共享指针保存，GUI 定时读取当前最新的完整帧，而不是为每一帧建立显示队列；当输入帧率高于界面刷新能力时，旧帧被新帧覆盖，从而避免显示延迟随时间累积。瀑布图采用 `Indexed8` 环形缓冲区保存历史行，仅对新增行和可见区域进行更新，降低大尺寸历史图像的内存占用与重复绘制成本。离屏渲染结果尚未就绪时，系统保留同步 Raster 绘制作为首帧和异常状态下的兜底路径，以保证界面能够正常显示。通过上述方法，系统在不依赖 GPU、OpenGL、EGL 或 `QOpenGLWidget` 的前提下形成了可部署的实时频谱显示链路，并以不低于 30 FPS 作为显示目标；其中板端实际帧率、延迟和 CPU 占用仍应结合目标屏幕、Qt QPA 后端及最终程序版本进行实测确认。
