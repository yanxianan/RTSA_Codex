# 数据流全景详解 —— 从射频信号到屏幕像素

> 本文把整条链路拆成八段，逐段讲清"数据在哪、谁在搬、用什么方式搬、什么时候会被丢掉"。
> 所有细节都对应当前仓库的 `src/app/main.cpp`、`src/ui/MainWindow.cpp`、`src/sources/`、`src/core/`、`src/plot/` 与 `driver/DMA/`。

---

## 0. 先看全景

```
   ①物理世界        ②PL（FPGA）              ③DDR 内存            ④内核
  ┌─────────┐    ┌──────────────┐      ┌──────────────┐    ┌──────────────┐
  │ 射频信号 │───►│ DDC→加窗→FFT │─AXI─►│ 32 MiB 环形   │───►│ rtsa_dma.ko  │
  │ (天线/源)│    │ 幅度/功率转换 │Stream│ 缓冲(128 槽)  │中断│ ioctl+mmap   │
  └─────────┘    └──────────────┘      └──────────────┘    └──────┬───────┘
                                                                  │ /dev/rtsa_dma
   ⑧屏幕           ⑦GUI              ⑥最新帧          ⑤处理管线     │
  ┌─────────┐    ┌──────────────┐   ┌──────────┐   ┌──────────┐   │
  │像素点亮  │◄───│ 频谱图/瀑布图 │◄──│LatestFrame│◄──│Pipeline  │◄──┤ ④用户态源
  └─────────┘    └──────────────┘   │  Store    │   │校验+轨迹 │   │ 字节→频谱帧
                                    └──────────┘   └──────────┘   └──────────┘
```

一句话概括：**硬件把频谱写进内存，内核把"内存变了"变成事件，用户态把字节翻译成频谱帧，管线做校验和轨迹处理，GUI 定时取最新一帧画到屏幕上。**

整条链路里，**数据本身只被搬动两次**：一次是 DMA 从 PL 搬进 DDR（不占 CPU），一次是 CPU 把原始整数换算成浮点 dBFS 值。其余所有环节都只是"传引用"和"读"，没有大规模拷贝。这是能跟上几十甚至几百 MB/s 的根本原因。

---

## 1. 先建立直觉：这条流水线上有四个"活着的东西"

理解数据流之前，先要知道谁在动。整个程序里有四个并发执行体：

| 执行体 | 职责 | 关键约束 |
|---|---|---|
| **GUI 主线程** | Qt 事件循环、控件更新、最终贴图 | 绝不能阻塞等待数据 |
| **采集线程** | 生成模拟数据，或从 DMA 取数据 | 一个数据源一个线程 |
| **离屏渲染线程** | 把频谱画到内存图片上 | 只处理最新任务 |
| （内核侧）中断处理 | DMA 完成时记录元数据并唤醒 | 不能睡眠 |

注意一个容易被误解的点：**没有"处理线程"**。帧校验、轨迹处理、发布这些动作，是在**采集线程里同步做完的**。源码里出现过"CPU0/1/2 多核异步"之类的注释，那是历史残留，不是实现事实。

---

## 2. 起点：数据从哪来

程序启动时（`main.cpp`）会解析命令行，决定用哪种数据源：

```
rtsa_app --source simulated   # 软件模拟源（PC 上用）
rtsa_app --source dma         # 真实 DMA 源（板子上用）
```

两种源实现同一个接口 `ISpectrumSource`，所以**从这一层往上，所有代码都不知道数据到底从哪来**。这是整个架构最重要的解耦点。

### 2.1 模拟源路径

`SimulatedSpectrumSource` 在自己的线程里循环生成频谱：

1. **取一份配置快照**（加锁拷贝，避免和界面线程改参数打架）。
2. **检查配置是否变过**（`configurationEpoch`）。变了就重新给随机数发生器播种——这样同一套配置永远产生同一串数据，方便复现测试。
3. **生成一帧**：先给所有频点填噪声底（用 xorshift32 随机数加三角分布），再把每个启用的音调按高斯形状叠加到对应频点附近，再叠加扫频信号，最后按概率叠加瞬态。
4. **注入故障**（如果配置开了）：按帧数间隔制造序号跳变、NaN 异常帧、突发帧。
5. **交给回调**：`sink(frame)`。
6. **按配置速率节流**：不限速就直接下一轮；帧间隔很短（不超过 2ms）时用自旋等待；很长（超过 10ms）时用条件变量等待，保证停止响应及时。

注意第 3 步：**模拟源直接生成"FFT 之后"的频谱值，不生成时域数据，也不做 FFT。** 它模拟的是 PL 的输出，不是 ADC 的输入。

### 2.2 DMA 路径

真实链路的源头在 PL 里：射频信号经过 DDC（数字下变频）降到基带、加窗、做 FFT、再转成幅度或功率值，然后通过 AXI4-Stream 推给 AXI DMA。

**这一段目前是仓库之外的**——PL 的 RTL 不在这个仓库里，只有设备树里为 DMA 预留的节点。所以论文里描述这一段时要注明是"外部实现"。

## 3. 第一段：硬件把数据写进内存（完全不经过 CPU）

AXI DMA 配置成 S2MM（Stream to Memory-Mapped）方向，也就是"从外设流搬到内存"。它把 PL 推来的数据直接写进 DDR 里一块**预先分配好的连续内存**。

这块内存有多大？

```
128 个槽位 × 每槽 256 KiB = 32 MiB
```

为什么是 256 KiB？因为最大配置是 65536 个频点、每点 4 字节，正好 256 KiB。也就是说**一个槽位刚好装得下最大的一帧**。

为什么是 128 个槽位？因为要在"硬件生产"和"软件消费"之间留缓冲。128 个槽位在 1000 帧/秒下能顶 128 毫秒——软件即使卡顿一小会儿，硬件也不会立刻因为没地方写而丢数据。

**这一段的关键性质：CPU 全程不参与。** DMA 引擎自己完成搬运，写完之后发一个中断。

```
PL ──AXI4-Stream──► AXI DMA ──写 DDR──► 槽位 i 填满 ──► 触发中断
                                          （数据就停在这里不动了）
```

---

## 4. 第二段：内核驱动把"内存变了"变成"事件"

中断到来时，驱动注册的回调 `rtsa_dma_rx_callback` 被调用（运行在中断上下文）。它只做最少的事：

1. **查这一帧的真实长度**：问 DMA 引擎还剩多少字节没传（residue），用 `256 KiB - residue` 算出实际长度。这是为了支持 PL 发短包的情况。
2. **加自旋锁**，保护共享状态。
3. **填元数据**：帧序号（全局计数器自增）、时间戳（`ktime_get_ns`）、实际长度、状态码。
4. **把槽号写进完成队列**：注意写的是**槽号**（一个整数），不是数据本身。数据一直躺在 DDR 里不动。
5. **唤醒等待者**：`wake_up_interruptible`，让正在 poll 的采集线程醒来。

如果完成队列满了（软件消费太慢），驱动会记录一次溢出，然后**把这个槽位重新提交给硬件继续用**——否则每溢出一次就永久少一个槽，十几次之后 DMA 直接停摆。

用户态通过四种方式和驱动打交道：

```
ioctl(START)    启动接收，把 128 个槽位全部交给硬件
mmap            把 32 MiB 映射到自己的地址空间（只做一次）
poll            睡眠等待"有数据了"
ioctl(DEQUEUE)  取出一个已完成的槽号
ioctl(QUEUE)    用完把槽号还回去
```

**mmap 这一步是性能关键**：映射之后，用户态读数据就是普通的内存读，没有任何系统调用开销、没有内核拷贝。

## 5. 第三段：用户态数据源把字节翻译成频谱帧

`DmaSpectrumSource` 在自己的线程里跑主循环：

```
打开设备 → mmap 32 MiB → ioctl(START) → 进入循环

循环：
  1. poll 等待可读（超时 100ms，为了能及时响应停止请求）
  2. 批量取已完成槽位，每轮最多 64 个
  3. 对每个槽位：
       - 判断是否到了"该发布"的时间（默认 60 FPS，即 16.7ms 一次）
       - 到了：把这块内存的前 binCount×4 字节拷到临时缓冲，记下要发布
       - 没到：只计数，不拷贝
       - 无论哪种情况，立刻 ioctl(QUEUE) 把槽位还给硬件
  4. 如果这一轮安排了发布：
       - 建一个频谱帧对象
       - 按需做 FFT Shift（把 DC 移到中心）
       - 把每个 int32 原始值换算成 dBFS：20×log10(|raw| / 2^31)
       - 填元数据（序号、时间戳来自驱动；中心频率、带宽来自配置）
       - 调 sink(frame) 交给管线
```

这里有两个设计要点值得注意：

**第一，先还槽位，再做换算。** 第 3 步里"立刻归还"是硬性要求——硬件等着这块内存继续接收下一帧。如果先做浮点运算再归还，高吞吐时硬件就会因为拿不到空闲槽而丢数据。所以代码里的顺序是：把数据拷到临时缓冲 → 立刻归还槽位 → 再做换算。

**第二，不是每一帧都送给界面。** 硬件可能每秒给上千帧，但人眼和屏幕只需要几十帧。所以按 `uiRefreshRateHz`（默认 60）节流，只有到点的那些帧才做拷贝和换算，其余只计数。这样 CPU 不会被"没人看的帧"浪费掉。

换算出来的帧长这样：

```
SpectrumFrame {
    metadata {
        sequence            ← 来自驱动（硬件帧计数）
        publicationSequence ← 由管线赋值（发布序号）
        timestampNs         ← 来自驱动（完成时间戳）
        centerFrequencyHz / spanHz / binCount
        unit = Dbfs, calibrated = false
        configurationEpoch
    }
    bins[]  ← float 数组，单位 dBFS
}
```

## 6. 第四段：处理管线（校验 + 轨迹）

数据源调用的 `sink` 回调，在 `MainWindow` 构造时被绑定成一句话：

```
source_->setFrameSink([this](const SpectrumFramePtr& frame) {
    return pipeline_.submit(frame);
});
```

所以**采集线程直接进入管线**，没有队列、没有转交。`SpectrumPipeline::submit` 做三件事：

**1. 校验。** 检查帧是否自洽（`binCount` 和数组长度一致且非空）、所有数值是否有限、频点数是否至少 2、带宽是否为正、中心频率是否有限。任何一项不满足，就计入 `invalidFrames` 并返回 false，**不抛异常**。

**2. 轨迹处理。** 交给 `TraceProcessor::process`：

| 模式 | 行为 |
|---|---|
| Clear/Write | 直接返回原帧，不做任何处理 |
| Average | 用 1/n 递推系数做指数平滑 |
| Max Hold | 逐点取历史最大值 |
| Min Hold | 逐点取历史最小值 |

这里有个重要规则：**如果频点数、中心频率、带宽、单位或 `configurationEpoch` 变了，历史立刻重置**，绝不跨配置混合。否则会出现"新旧两套参数叠在一起"的鬼影。

注意 Clear/Write 模式返回的是**原始帧本身**（不复制），而其他模式会从帧池里取一个新帧。这样最常见的模式零开销。

**3. 发布。** 给帧打上发布序号（`publicationSequence`），然后存进 `LatestFrameStore`。

整个过程在采集线程内同步完成，耗时会被记录在 `lastProcessingNanoseconds_` 里，界面上显示为"处理耗时"（典型值不到 1 ms）。

## 7. 第五段：最新帧存储（为什么不是队列）

`LatestFrameStore` 只有三个操作，实现也极简：

```
publish(frame)  → 原子地替换内部指针
latest()        → 原子地读取当前指针
clear()         → 原子地置空
```

用的是 `std::atomic_load/store` 配合 `shared_ptr`，读者拿到的是一个**不可变的 const 帧**，不会看到半成品。

**为什么用"最新帧"而不是队列？** 这是整个设计里最关键的一个取舍。

如果用一个队列：界面消费慢的时候，队列会越积越长，用户看到的画面会越来越滞后——最后可能延迟好几秒，而且内存持续增长。

用"最新帧"：新帧直接覆盖旧帧，**队列深度永远是 0 或 1**。界面慢的时候只是跳过一些帧，但看到的永远是"此刻最新的频谱"，延迟稳定。

对频谱仪这种"看当前状态"的仪器，这个取舍是对的。代价是：中间那些帧被丢掉了，所以统计里必须单独记一个"显示跳过帧"，不能假装什么都没发生。

---

## 8. 第六段：主窗口的定时器（显示节流）

主窗口在构造时创建两个定时器：

```
renderTimer_      PreciseTimer, 10 ms   → refreshDisplay()    （约 100 次/秒）
statisticsTimer_          500 ms        → refreshStatistics()
```

`refreshDisplay()` 每次只做四件事：

```
1. 从 LatestFrameStore 取当前最新帧
2. 如果这一帧的 publicationSequence 和上次显示的相同 → 直接返回（没有新数据）
3. 如果序号跳了不止 1 → 把差额累加进 displaySkippedFrames_
4. plot_->setFrame(frame)；并在瀑布图可见时 waterfallPlot_->addFrame(frame)
```

注意第 1 步的语义：**不是"等数据来"，而是"看看现在有没有新的"**。有就画，没有就什么都不做。主线程永远不会被数据阻塞。

第 2 步那个"序号相同就返回"很关键。定时器每 10ms 触发一次，但数据可能每 16.7ms 才来一帧，所以大约有一半的触发是空跑——不做任何绘制，不浪费 CPU。

第 3 步的 `displaySkippedFrames_` 就是"输入帧率高于显示帧率"的量化证据。这个数字出现在状态栏里，用户能直观看到"我跳过了多少帧"。

`refreshStatistics()` 每 500ms 更新一次状态栏，读的是**采集侧的统计**（帧率、数据率、丢帧）和**管线侧的统计**（提交数、发布数、无效帧、处理耗时），再加上显示侧的帧率和延迟 P95。这些数字来源不同、口径不同，所以界面上必须分开显示，不能合成一个"丢帧"。

## 9. 第七段：两条并行的显示支路

拿到帧之后，数据分成两路，去往两个不同的控件。

### 9.1 频谱图支路（异步渲染）

`SpectrumPlotWidget::setFrame()` 做的事很少：

```
1. 保存帧指针，同步 Marker 位置（按频率重新映射到 bin）
2. 打包一个 RenderContext（帧 + 尺寸 + 绘图区 + 外观参数 + Marker 位置）
3. 加锁写入 pendingContext_，置标志
4. notify_one 唤醒离屏渲染线程
```

注意第 3 步是**覆盖**而不是入队。所以渲染线程醒来时永远只看到最新那一帧。

离屏渲染线程 `workerLoop` 被唤醒后：

```
1. 把 pendingContext_ 搬走
2. renderToImage()：
     - 静态层脏了就重建（网格、坐标、文字）
     - 复用目标图缓冲，把静态层复制过去
     - 按像素列做包络降采样，生成曲线点集
     - 画曲线和 Marker
3. 把成品图放进 frontImage_（加锁）
4. 用队列连接通知主线程"绘图区该重绘了"
```

主线程收到通知后进入 `paintEvent`，执行一句：

```
painter.drawImage(dirty.topLeft(), frontImage_, dirty);
```

**只贴这一块矩形**，不做任何几何计算、不画任何文字。

### 9.2 瀑布图支路（同步写入）

`WaterfallPlotWidget::addFrame()` 走的是另一条路，因为它不需要复杂渲染：

```
1. 按列取最大值，把 binCount 个频点压成绘图区宽度个数值
2. 头指针向前移一格
3. 每个数值经色表映射成 0~255 的色号，写进环形缓冲的那一行
4. 只标记瀑布绘图区重绘
```

每帧只写一行像素，稳态下不做任何整图搬移。绘制时把环形缓冲按逻辑顺序拆成两段贴到屏幕上。

---

## 10. 第八段：从内存图片到屏幕像素

到这里，数据已经变成了内存里的一张图片。最后一步是把它显示到屏幕上，这一步由 Qt 的平台插件（QPA）负责：

```
QImage（内存图片）
    ↓ Qt 合成
窗口 backing store
    ↓ QPA 插件（linuxfb / XCB / Wayland / DRM-KMS）
/dev/fb0 或显示控制器
    ↓
屏幕像素
```

**这一段是当前项目里证据最弱的一环。** 源码能证明应用内部用的是 16 位 RGB 图片，但**不能**证明从图片到 framebuffer 之间没有再做格式转换——那取决于 Qt 平台插件的实现、framebuffer 的实际像素格式、以及窗口系统是否介入。这个必须在目标板上实测才能下结论。

---

## 11. 完整时序：一帧数据的旅程

把上面八段串起来，一帧数据从产生到显示大致经历这些时刻：

| 时刻 | 发生什么 | 在哪 |
|---|---|---|
| T0 | PL 完成一帧 FFT，开始推 AXI-Stream | PL |
| T0+ε | AXI DMA 写进槽位 i，写满触发中断 | 硬件 |
| T0+ε | 回调填元数据、槽号入队、唤醒 poll | 内核中断 |
| T1 | 采集线程从 poll 醒来，批量取槽 | 采集线程 |
| T1+ε | 判断是否到发布时机；到则拷贝并归还槽位 | 采集线程 |
| T1+ε | 换算 dBFS、填元数据、调 sink | 采集线程 |
| T1+ε | 管线校验 → 轨迹处理 → 打发布序号 → 存最新帧 | 采集线程（同步） |
| T2 | 10ms 定时器触发，发现序号变了 | GUI 主线程 |
| T2+ε | setFrame → 打包上下文 → 唤醒渲染线程 | GUI 主线程 |
| T3 | 渲染线程画完整幅图，发布 frontImage_ | 离屏线程 |
| T3+ε | 通知主线程，主线程贴脏区 | GUI 主线程 |
| T4 | QPA 合成、写 framebuffer | Qt 平台插件 |

从 T0 到 T4 就是"端到端显示延迟"，界面上用 `framePainted` 信号带回的发布时间戳和当前时间之差来估算，并统计最近 256 个样本的 P95 值。

**PC 上的历史数据**：16384 点、1000 帧/秒输入时，显示约 33.7 FPS，P95 延迟约 16.5 ms。这个数字不能外推到 ZU47DR 板端。

## 12. 数据在哪些地方会被丢掉

这是最容易被含糊过去的部分。整条链路上有**四个不同的丢弃点**，原因和含义完全不同：

| 丢弃点 | 原因 | 统计字段 |
|---|---|---|
| **驱动完成队列溢出** | 用户态消费太慢，队列满了 | 只在 dmesg 里打日志（用户态拿不到） |
| **用户态发布节流** | 硬件帧率高于 UI 刷新率，故意不送界面 | `producedFrames_` 与送出的帧数之差 |
| **管线校验失败** | 帧自洽性检查没过（点数不符、含 NaN 等） | `invalidFrames_`、`processingDrops_` |
| **GUI 跳过显示** | 显示定时器触发时旧帧已被覆盖 | `displaySkippedFrames_` |

**这四类必须分开报告，不能合成一个"丢帧"数字。** 比如"输入 1000 FPS、显示 35 FPS"看起来像丢了很多帧，但那其实是**设计如此**的节流，不是故障；而驱动队列溢出才是真正的数据丢失。

当前实现的一个已知缺口是：**第一类（驱动溢出）没有暴露给用户态**，所以现在无法从界面上区分"是硬件丢的"还是"是我们故意节流的"。这是后续要补的。

## 13. 线程与所有权规则汇总

把这套设计里所有"谁拥有数据"的规则集中列一遍，这是理解并发正确性的钥匙：

| 数据 | 拥有者 | 规则 |
|---|---|---|
| DMA 槽位内存 | 硬件与软件交替 | QUEUED 期间归硬件，用户态绝不能读；COMPLETED/FREE 期间归软件 |
| 原始 int32 临时缓冲 | 采集线程 | 只在采集线程内使用，拷贝出来就立刻归还槽位 |
| `SpectrumFrame` | 通过 `shared_ptr` 共享 | 发布后视为不可变，任何读者只能读不能改 |
| `pendingContext_` | 主线程写、渲染线程读 | 互斥量保护；只保留最新一个 |
| `frontImage_` | 渲染线程写、主线程读 | 互斥量保护；利用 Qt 隐式共享做浅拷贝 |
| 瀑布环形缓冲 | GUI 主线程独占 | 只在 `addFrame` 里写，不跨线程 |

一条总原则：**跨线程传递的永远是"不可变的完整对象"，而不是"正在被写的缓冲区"。** 违反这条就会出现撕裂数据，而且往往几十次才复现一次，极难排查。

## 14. 为什么这么设计（关键取舍）

把整条链路上的设计决策归纳一下，这些都是论文里值得写的"设计理由"：

1. **为什么用 DMA 而不是 CPU 搬运？** 数据率太高（最大约 262 MB/s），CPU 搬不过来。
2. **为什么用环形缓冲而不是单缓冲？** 单缓冲要求硬件和软件严格交替，任何抖动都会丢数据。环形缓冲提供了 128 帧的容错余量。
3. **为什么用 mmap 而不是 read？** read 需要一次内核到用户态的拷贝，65 MB/s 下这个拷贝很贵。mmap 之后用户态直接读，零拷贝。
4. **为什么管线在采集线程里同步跑？** 因为处理本身很快（不到 1ms），引入独立线程和队列只会增加复杂度和延迟，收益不明显。**但这也意味着：如果处理变慢，会直接反压采集。** 这是当前架构的已知边界。
5. **为什么用最新帧而不是队列？** 见第 7 节——保证延迟稳定、内存不涨，代价是主动丢帧。
6. **为什么渲染要单独开线程？** 因为软件光栅化很贵（几毫秒到几十毫秒），放在主线程会让界面卡顿。
7. **为什么采集侧要节流到 60 FPS？** 因为人眼和屏幕不需要 1000 FPS，而换算和拷贝是有成本的。

## 15. 几个常见误解

**误解一："输入 1000 FPS、显示 35 FPS，说明性能不够。"**
不一定。显示 35 FPS 是"最新帧优先"策略的预期结果，不代表处理不过来。要看的是：处理耗时是否稳定、P95 延迟是否达标、有没有真正的数据丢失。

**误解二："管线是多线程流水线。"**
不是。管线在采集线程里同步执行，没有独立线程、没有队列、没有多核负载均衡。

**误解三："模拟源和 DMA 源走两条完全不同的路。"**
不是。从 `FrameSink` 往上，两者完全一致。差异只在"帧从哪来"这一段。

**误解四："数据经过了很多次拷贝。"**
只有两次实质拷贝：DMA 写内存（硬件做）、原始整数换算成浮点（CPU 做）。其余环节传的都是指针或引用。

**误解五："`queueDepth` 是处理队列深度。"**
不是。这个字段目前恒为 0，是预留位。当前架构根本没有处理队列。

## 16. 附：一帧里每个字段的来源

最后把帧元数据的出处列清楚，这在排查"数值不对"时非常有用：

| 字段 | 来源 | 备注 |
|---|---|---|
| `sequence` | 驱动（`rtsa_buffer_info.sequence`） | 硬件/驱动侧帧计数，用于检测丢帧 |
| `timestampNs` | 驱动（`ktime_get_ns`） | 驱动完成时间戳，不是 PL 的采样时间 |
| `publicationSequence` | 管线 | 发布序号，界面用它判断"有没有新帧" |
| `centerFrequencyHz` / `spanHz` | 用户态配置 | **不在载荷里**，来自 `DmaSourceConfig` |
| `binCount` | 用户态配置 | 同上 |
| `unit` | 固定 `Dbfs` | 当前只有这一种 |
| `calibrated` | 固定 `false` | 未标定，所以 dBFS 不等于 dBm |
| `configurationEpoch` | 用户态配置 | 配置变化时自增，用于触发轨迹重置 |
| `bins[]` | 载荷换算 | `20×log10(|raw| / 2^31)`，绝对值不超过 1 时取 -140 dBFS |

**这张表里最关键的一行是 `centerFrequencyHz` 和 `spanHz` 来自配置而不是载荷。** 也就是说：如果 PL 实际输出的频段和用户态配置不一致，程序不会察觉——它会按配置画出错误的频率轴。这是当前协议缺少版本化帧头带来的直接风险，也是"必须冻结 PL/PS 协议"这条任务的根本原因。
