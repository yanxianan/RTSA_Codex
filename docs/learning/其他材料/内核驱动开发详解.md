# 内核驱动开发详解 —— RTSA AXI DMA 字符设备驱动

> 对应任务分解里的 D 模块。本文按"为什么必须写 → 先懂哪几个概念 → 内存怎么摆 → 生命周期 → 用户态接口 → 并发难点 → 已知缺口 → 怎么编译调试 → 从零实施的顺序"展开。
> 所有描述都对应当前仓库的 `driver/DMA/rtsa_dma_driver.c`、`rtsa_dma_uapi.h` 和 `system-user.dtsi`，不是泛泛的教程。

---

## 0. 为什么这件事必须写驱动

先明确一个前提：**频谱数据不是 CPU 去"取"回来的，是硬件自己写进内存的。**

PL 端的 FFT 算完一帧频谱后，会通过 AXI4-Stream 把数据推给 AXI DMA；AXI DMA 再把数据直接写进 PS 的 DDR 内存。整个过程 CPU 不参与搬运，这叫 DMA（Direct Memory Access）。这样做的原因是数据量太大——16384 点、每点 4 字节、每秒 1000 帧，就是约 65 MB/s，如果让 CPU 一个字节一个字节搬，什么都别干了。

但"硬件自己往内存写"带来三个问题，必须由内核来解决：

1. **内存必须是物理连续的。** DMA 硬件只认物理地址，而用户态拿到的都是虚拟地址，中间隔着页表。而且这些内存还得是"一致性内存"（coherent），保证 CPU 看到的内容和硬件写进去的一致，不需要手动刷缓存。
2. **硬件写完了要通知软件。** 这靠中断实现，而中断处理属于内核。
3. **用户态不许直接操作硬件寄存器。** 配 DMA 描述符、启动通道这些动作在内核态做，用户态只应该看到一个文件。

所以驱动的本质工作是：**把"一块会自己变的内存 + 一个会响的中断"包装成一个用户态能安全使用的文件接口。** 用户态打开 `/dev/rtsa_dma`，用几个 ioctl 命令控制启停和取数据，用 mmap 直接读那块内存。

换个说法：驱动是硬件和应用程序之间的翻译官。翻译没做好，上面写得再漂亮也拿不到正确数据。

## 1. 动手前要先懂的六个概念

**DMA**：硬件直接把数据从 A 搬到 B，不占用 CPU。本项目里是从 AXI-Stream（外设）搬到 DDR（内存），方向叫 DEV_TO_MEM。

**dmaengine**：Linux 内核里对各类 DMA 控制器的统一抽象层。你不需要自己写寄存器操作，只要向它申请一个通道、准备一个"描述符"（描述"从哪搬到哪、搬多少、搬完叫我"）、提交它。

**字符设备**：一种设备模型，对应 `/dev/` 下的一个文件。用户态通过 open、read、write、ioctl、mmap、poll 这些标准文件操作和它打交道。本项目没有用 read/write，而是用 ioctl 发命令、mmap 拿数据。

**一致性内存（coherent）**：用 `dma_alloc_coherent` 申请的内存，CPU 和 DMA 看到的是同一份数据，不用手动同步缓存。代价是这类内存通常性能略低、且数量有限（本项目靠设备树预留 128 MB CMA 来保证能申请到 32 MiB 连续内存）。

**环形缓冲**：固定数量的槽位循环使用。写指针走到末尾就回到开头。本项目有 128 个槽位，硬件填一个、软件取一个，靠头尾指针判断空和满。

**中断上下文**：DMA 完成回调运行在中断环境里。这里有严格限制——**不能睡眠、不能分配内存、不能调用可能阻塞的函数、不能直接往用户态拷贝数据**。这是新手最容易踩的坑，后文会反复提到。

## 2. 数据通路全景

```
        PL（FPGA）                          PS（Linux）
   ┌────────────────┐              ┌──────────────────────────────┐
   │ DDC → 窗 → FFT │  AXI4-Stream │  AXI DMA（S2MM，外设→内存）   │
   │ 幅度/功率转换   │ ───────────► │            ↓ 写入            │
   └────────────────┘              │  32 MiB 一致性缓冲（128 槽） │
                                   │            ↓ 完成中断         │
                                   │  rtsa_dma.ko（本驱动）        │
                                   │            ↓ /dev/rtsa_dma    │
                                   │   ioctl / mmap / poll         │
                                   │            ↓                  │
                                   │  DmaSpectrumSource（用户态）  │
                                   └──────────────────────────────┘
```

关键点：**数据从头到尾只被搬了一次**（DMA 写进内存），之后 CPU 只是"读"，不再拷贝。这是能跑满带宽的前提。用户态读到的就是硬件写进去的那块内存，中间没有额外复制。

## 3. 两个核心数据结构

### 3.1 `struct dma_slot` —— 一个槽位

```
struct dma_slot {
    struct rtsa_dma_dev *rtsa;   // 反向指针，回调里要靠它找到设备
    __u32 index;                 // 槽号 0..127
    void *vaddr;                 // 这块内存在 CPU 侧的虚拟地址
    dma_addr_t paddr;            // 同一块内存在 DMA 侧的物理地址
    struct rtsa_buffer_info info;// 这一帧的元数据（序号/时间戳/长度/状态）
    enum slot_state state;       // FREE / QUEUED / COMPLETED
    dma_cookie_t cookie;         // 本次提交的凭据，查传输状态要用
};
```

要点：

- `vaddr` 和 `paddr` 是**同一块内存的两个地址**，一个给 CPU 用，一个给硬件用。驱动负责维护这对映射关系，用户态只关心偏移量。
- `info` 是这一帧的"身份证"。用户在取走数据的同时拿到它，才知道这帧的序号、时间戳和实际长度。
- `state` 是槽位状态机，是并发正确性的核心（见第 8 节）。

### 3.2 `struct rtsa_dma_dev` —— 整个设备

```
struct rtsa_dma_dev {
    struct platform_device *pdev;    // 对应的平台设备
    struct cdev cdev;                // 字符设备对象
    dev_t dev_node;                  // 设备号
    struct class *class;
    struct device *device;           // /dev/rtsa_dma 对应的 device

    struct dma_chan *rx_chan;        // 申请到的 DMA 通道
    struct dma_slot slots[128];      // 128 个槽位

    void *dma_base_vaddr;            // 整块内存的 CPU 基址
    dma_addr_t dma_base_paddr;       // 整块内存的 DMA 基址
    size_t dma_total_size;           // 32 MiB

    wait_queue_head_t rx_wait;       // 等待队列，poll 用它睡眠和唤醒
    spinlock_t lock;                 // 保护下面这几个字段
    __u32 completed_head;            // 完成队列写指针
    __u32 completed_tail;            // 完成队列读指针
    __u32 completed_queue[128];      // 完成队列本体（存槽号，不存数据）

    unsigned long is_opened;         // 是否已被打开（排他）
    bool is_running;                 // 是否正在接收
    __u64 frame_seq;                 // 全局帧序号计数器
};
```

这里最容易看错的一点：**`completed_queue` 存的是"槽号"，不是数据。**

数据永远躺在 `dma_base` 那 32 MiB 里不动。完成队列只是一个 128 项的整数环，记录"第几个槽位已经填好了"。用户态从队列里取出一个槽号，然后去 32 MiB 里对应的偏移处读数据。这样设计的好处是元数据（队列）和载荷（缓冲）分离，队列操作极轻，不会拖慢中断。

## 4. 32 MiB 内存是怎么切出来的

驱动在 probe 阶段调用一次 `dma_alloc_coherent`，申请 128 × 256 KiB = 32 MiB 的连续内存。然后把这整块内存按固定步长切成 128 份：

```
slot[i].vaddr = dma_base_vaddr + i * 256KiB
slot[i].paddr = dma_base_paddr + i * 256KiB
```

为什么是"一次申请、自己切"，而不是申请 128 次 256 KiB？两个原因：

1. **物理连续。** 128 次小申请很可能拿到不连续的内存，DMA 描述符就得写 128 个，管理和性能都变差。
2. **一次成功率高。** 大块连续内存在系统跑久了以后很难申请到，所以必须在 probe 阶段一次性拿到。设备树里预留 128 MB CMA 就是为了保证这一步能成功。

为什么每槽是 256 KiB？因为最大配置是 65536 点、每点 4 字节，正好 256 KiB。换句话说，**这个数字是按最大帧长定的，改最大频点数就要同步改这里**，而且驱动、用户态、测试工具三处都要改（`rtsa_dma_uapi.h` 里的宏就是为此存在的）。

## 5. 生命周期：从模块加载到卸载

### 5.1 probe：设备被识别时执行

内核发现设备树里有个 `compatible = "rtsa,spectrum-dma"` 的节点，就会调用驱动的 probe 函数。它按顺序做八件事：

1. **设置 DMA 地址掩码**：先试 64 位，失败退回 32 位。ZU47DR 的 DDR 地址可能超过 4 GB，所以必须优先试 64 位，否则 DMA 根本寻不到高地址内存。
2. **分配设备私有结构体**：用 `devm_kzalloc`。带 `devm_` 前缀的意思是"设备销毁时自动释放"，省掉手工清理。
3. **初始化同步原语**：自旋锁和等待队列。注意这两样必须在任何可能并发的代码之前初始化好。
4. **申请 DMA 通道**：`dma_request_chan(&pdev->dev, "rx_chan")`，名字要和设备树里 `dma-names` 完全一致，对不上就会失败。
5. **申请 32 MiB 一致性内存**。
6. **切分槽位**：填好每个槽位的 vaddr、paddr、index、state。
7. **注册字符设备**：申请设备号 → 初始化 cdev → 添加 cdev → 创建设备类 → 创建设备节点。这一步做完 `/dev/rtsa_dma` 才会出现。
8. **保存私有数据**：`platform_set_drvdata`，这样 remove 的时候能取回来。

### 5.2 错误回滚：为什么要用 goto

probe 里有 7 个可能失败的步骤。如果第 5 步失败，前面申请的设备号和通道必须释放；如果第 7 步失败，前面更多资源要释放。

内核代码里标准的写法是"阶梯式标签"：

```
err_class_destroy:   class_destroy(...);
err_cdev_del:        cdev_del(...);
err_unregister_region: unregister_chrdev_region(...);
err_free_dma:        dma_free_coherent(...);
err_free_chan:       dma_release_channel(...);
```

失败时 `goto` 到对应的标签，就会顺着往下把该释放的都释放掉。这不是"goto 不好"的场合——在内核里这是最清晰、最不容易漏释放的写法。**写驱动时资源泄漏比崩溃更难查**，因为泄漏往往要跑很久才暴露。

### 5.3 remove：逆序释放

卸载模块时执行，顺序基本是 probe 的逆序，但有一点特别重要：

**第一步必须是无条件停止 DMA 硬件。** 代码里先 `dmaengine_terminate_sync` 把通道停掉，再释放内存。如果反过来先释放内存、硬件还在往里写，就会写到已释放的物理地址上，轻则数据错乱，重则总线异常甚至死机。

这个顺序不能靠"应该没问题"来赌，必须无条件先停硬件。

## 6. 用户态看到的接口

驱动对外暴露的东西非常少：一个设备节点 `/dev/rtsa_dma`，加 4 个 ioctl 命令、mmap 和 poll。

### 6.1 `RTSA_IOC_START` —— 开始接收

做四件事：

1. 检查是否已经在运行，是就返回 `-EBUSY`（不能重复启动）。
2. 置 `is_running = true`，把完成队列的头尾指针清零，所有槽位状态复位为 FREE。
3. 释放锁，然后**把 128 个槽位全部提交给 DMA 硬件**。这一步是让硬件知道"这 128 块内存我都给你了，你随便往里写"。
4. 任何一个提交失败，就回滚：把 `is_running` 置回 false、终止通道、返回错误。

注意第 3 步是"全部提交"，也就是启动瞬间就把整个环交给硬件。之后每被取走一个槽，用户态再还回来一个，形成循环。

### 6.2 `RTSA_IOC_DEQUEUE` —— 取一个已完成的槽

1. 先把返回结构体 `memset` 清零。这一步是**安全措施**，防止结构体里的填充字节把内核栈上的残留数据泄露给用户态。
2. 检查队列是否为空，空就返回 `-EAGAIN`（不是错误，是"暂时没数据"）。
3. 从队列尾取一个槽号，尾指针前移。
4. 把该槽的元数据拷出来，**把槽位状态改成 FREE**（表示这块内存硬件可以重新写了）。
5. 释放锁后，用 `copy_to_user` 把元数据交给用户态。注意拷贝必须在解锁之后做——在锁里做拷贝会拉长临界区。

用户态拿到槽号后，自己去 mmap 的那块内存里按 `index × 256KiB` 找数据。

### 6.3 `RTSA_IOC_QUEUE` —— 归还槽位

用户态用完数据后，把槽号还回来，驱动重新提交给硬件。这里有三个检查，每个都对应一类真实的 bug：

1. **槽号越界检查**：防止用户态传一个非法值把内核数组读越界。
2. **`is_running` 检查**：没在运行就返回 `-ENODEV`。
3. **重复入队检查**：如果这个槽已经是 QUEUED 状态，返回 `-EBUSY`。

第三条是**防重入的关键**。用户态如果因为 bug 把同一个槽归还两次，硬件就会同时往同一块内存写两帧数据，结果是两帧都坏。代码里的做法是：在锁内就把状态预置成 QUEUED，然后再去提交描述符；提交失败再改回 FREE。这样即使在提交过程中有另一个线程来操作同一个槽，也会被第三条检查挡住。

### 6.4 `RTSA_IOC_STOP` —— 停止接收

置 `is_running = false`、所有槽位复位、调用 `dmaengine_terminate_sync` 真正停掉硬件、唤醒所有等待者（让正在 poll 的进程知道设备停了）。

### 6.5 `mmap` —— 把 32 MiB 映射到用户态

两个安全检查：偏移必须为 0（不许从中间开始映射），映射长度不能超过 32 MiB。然后调用 `dma_mmap_coherent` 把内核里那块一致性内存映射到用户地址空间。

映射之后，用户态读这块内存**没有任何系统调用开销**，也不需要内核拷贝——这就是为什么能跟上 65 MB/s 甚至 260 MB/s 的数据率。

### 6.6 `poll` —— 等待数据

用户态不想一直轮询（浪费 CPU），就用 poll 睡眠等待。驱动做两件事：

1. `poll_wait` 把自己的等待队列登记进去（这样有数据时能被唤醒）。
2. 检查当前状态：设备已停就报 `EPOLLHUP | EPOLLERR`；队列非空就报 `EPOLLIN | EPOLLRDNORM`。

两者都没有，poll 就会睡眠，直到完成回调里的 `wake_up_interruptible` 把它叫醒。

## 7. 整个驱动最难的一段：完成回调

当 DMA 把一帧写进某个槽位，硬件会触发中断，内核最终调用驱动注册的回调 `rtsa_dma_rx_callback`。这段代码运行在中断上下文，是整个驱动最需要小心的部分。

它按顺序做：

1. **查实际传输长度**：`dmaengine_tx_status` 拿到剩余字节数（residue），用 `256 KiB - residue` 算出这一帧真实长度。这一步是为了支持 PL 发短包（比如 TLAST 提前拉高）的情况。
2. **加自旋锁**（`spin_lock_irqsave`，同时关中断，防止死锁）。
3. **如果设备已经停止**，把槽位标记 FREE 就直接返回，不做任何入队。
4. **填充元数据**：序号（全局计数器自增）、时间戳（`ktime_get_ns`）、实际长度、状态。
5. **入队，并检查是否溢出**——这是本项目最关键的一段逻辑，单独讲。
6. **解锁，然后唤醒等待者**。

### 7.1 溢出处理：为什么必须重新提交槽位

完成队列只有 128 个位置，而且为了区分"空"和"满"要牺牲一个，**实际容量是 127**。如果用户态消费得慢，队列会满。

原始写法遇到队列满时，只是丢弃这一帧然后返回。这会造成一个隐蔽但致命的问题：

> 这个槽位已经完成了，但没有入队，也没有归还给硬件。它就从"硬件可用池"里永久消失了。每溢出一次少一个槽，溢出十几次之后，硬件手上一个可用缓冲都没有了，DMA 直接停摆。

这个现象在板子上表现为"跑一会儿就再也不出数据了"，而且重启应用也没用，必须重载模块——非常难查。

当前代码的修复是：队列满时，把槽位状态改回 FREE，**立刻调用 `rtsa_submit_rx_slot` 把它重新提交给硬件**，让硬件能继续用这块内存接收下一帧。这样溢出的代价只是"这一帧数据丢了"，而不是"整个通道慢慢死掉"。

需要如实说明的是：**这个机制叫"自愈"，但它救的是通道，不是数据。** 已经因为队列满被丢弃的那一帧是找不回来的。所以不能据此宣称"绝不丢帧"——它的作用是让系统在过载后还能继续工作，而不是消除过载。

## 8. 槽位状态机：并发正确性的核心

每个槽位在任意时刻只能处于三种状态之一：

```
        ┌──────────────────────────────────────────┐
        │                                          │
        ▼                                          │
     FREE ──(START / QUEUE 提交描述符)──► QUEUED   │
        ▲                                    │     │
        │                                    │ 硬件完成中断
        │                                    ▼     │
        └──(DEQUEUE 取走 / 溢出丢弃)──── COMPLETED ┘
```

- **FREE**：空闲，可以被提交给硬件。
- **QUEUED**：已提交给硬件，正在接收数据。此时用户态绝不能读这块内存（会读到半帧）。
- **COMPLETED**：硬件写完了，数据有效，等待用户态取走。

所有状态迁移都必须在自旋锁保护下进行。任何一处漏锁，都会出现"用户态正在读、硬件同时在写"的撕裂数据，而且这种 bug 在测试环境里往往几十次才复现一次。

还有一条所有权规则要记住：**QUEUED 期间内存属于硬件，COMPLETED 和 FREE 期间属于软件。** 驱动通过状态机来强制这条规则。

## 9. 当前实现的已知缺口（诚实清单）

这部分是给毕业论文"不足与改进"一节准备的，也是后续要补的工作：

1. **没有校验 `info.size`。** 用户态按配置的频点数去读，但驱动返回的实际长度可能不足。如果实际只有 1 KB 而用户态按 64 KB 读，就会读到上一帧的残留数据。正确做法是用户态检查 `size >= binCount × 4`，不足就拒绝这一帧。
2. **溢出次数没有暴露给用户态。** 现在溢出只在 dmesg 里打一条限速日志，用户态统计不到，验收时无法给出"驱动侧丢了多少帧"这个数字。
3. **完成队列容量是 127 而不是 128。** 头尾指针判空满的方式决定了要牺牲一个位置。文档和注释里写的"128"指的是槽位数，不是队列容量，两者不能混。
4. **没有 reset 语义。** 如果 PL 侧重新加载 bit 或者断流，驱动没有显式的复位接口，只能靠 STOP + START 重建。
5. **单进程排他打开。** `is_opened` 位决定同时只能有一个进程打开设备。多客户端、多通道场景需要重新设计。
6. **UAPI 没有版本号。** 现在只有一组宏定义，没有协议版本字段，将来改结构体无法让用户态识别。
7. **没有错误分类。** 传输错误、超时、总线异常都归到同一个 `status` 字段，无法区分。

## 10. 设备树：驱动怎么被"发现"

驱动不会自己去扫描硬件，是内核根据设备树来匹配的。本项目在 `system-user.dtsi` 里的相关节点是：

```
&amba_pl {
    rtsa_dma_node {
        compatible = "rtsa,spectrum-dma";   // ← 和驱动的 of_match_table 对应
        dmas = <&axi_dma_0 0>;
        dma-names = "rx_chan";              // ← 和 dma_request_chan 的名字对应
        status = "okay";
    };
};

&axi_dma_0 {
    status = "okay";
};
```

三处必须一致，任何一处写错都会导致 probe 失败：

1. `compatible` 字符串要匹配驱动的 `of_device_id`。
2. `dma-names` 要匹配 `dma_request_chan` 里请求的名字。
3. `dmas` 要指向真实存在的 DMA 控制器节点。

另外，`reserved-memory` 里那 128 MB CMA 保留池是前置条件——没有它，`dma_alloc_coherent` 申请 32 MiB 连续内存很容易失败，probe 直接返回 `-ENOMEM`。

## 11. UAPI：内核和用户态之间的合同

`rtsa_dma_uapi.h` 是驱动和用户态**共同包含**的头文件，它定义了双方的契约：

- 两个常量：`RTSA_RING_BUFFER_COUNT`（128）和 `RTSA_BUFFER_SIZE`（256 KiB）。
- 一个结构体：`rtsa_buffer_info`，含 index、size、sequence、timestamp_ns、status，以及一个显式的 `reserved` 填充字段。
- 四个 ioctl 命令号，用 `_IO` / `_IOR` / `_IOW` 宏生成。

两个设计细节值得在论文里提：

**`reserved` 字段是故意留的。** 结构体里 `__u32` + `__u32` + `__u64` + `__u64` + `__u32` 加起来是 28 字节，不是 8 的倍数。加一个 `reserved` 补齐到 32 字节，一方面保证 64 位对齐（不同架构对未对齐访问的处理不一样），另一方面明确声明"这里将来可以扩展"，避免以后加字段改变结构体大小导致 ABI 断裂。

**非 Linux 分支提供了假的 ioctl 宏。** 头文件里 `#else` 分支把 `_IO`/`_IOR`/`_IOW` 定义成简单的位运算。这样上位机在 Windows 上编译时也能包含这个头文件而不会报错——虽然 Windows 上根本不会用到这些命令，但源码里引用常量的地方能编过。这是"让跨平台代码不需要到处写 `#ifdef`"的常见技巧。

## 12. 怎么编译、加载、调试

**交叉编译模块**（在 Linux 主机上，指向 PetaLinux 的内核源码树）：

```
make -C driver/DMA \
  KDIR=/path/to/petalinux/components/linux-xlnx \
  ARCH=arm64 \
  CROSS_COMPILE=aarch64-linux-gnu-
```

产物是 `rtsa_dma.ko`。

**在板子上加载并检查**：

```
insmod rtsa_dma.ko
lsmod | grep rtsa_dma
ls -l /dev/rtsa_dma
dmesg | tail -n 100
```

dmesg 里应该能看到 "RTSA DMA driver probed successfully, total size: 33554432 bytes"。看不到这条，说明 probe 失败了，往上翻找第一条错误信息——通常就是 `compatible` 不匹配、`dma-names` 写错，或者 CMA 内存不够。

**功能验证**：编译并运行 `dma_benchmark`，它会打印实时帧率、数据量、峰值位置和序号缺口。这是没有显示器时最快的连通性验证手段。

**排查思路**（按顺序排除）：

1. 设备节点不存在 → probe 失败，看 dmesg。
2. 能打开但 poll 一直超时 → PL 没在发数据，或者 TLAST 配置不对。
3. 有数据但数值不对 → 载荷格式或字节序理解错了，属于协议问题不是驱动问题。
4. 跑一会儿就停 → 大概率是完成队列溢出，看 dmesg 有没有 "Ring buffer overflow"。

## 13. 如果从零写这个驱动，建议的顺序

按这个顺序做，每一步都能独立验证，不会出现"全写完才发现跑不起来"：

1. **先把设备树节点和设备节点跑通**：probe 成功、`/dev/rtsa_dma` 出现，先不接 DMA。
2. **加 DMA 通道申请和内存分配**：确认 32 MiB 能申请到（这一步最容易卡住，CMA 配置不对就会失败）。
3. **实现 START 和完成回调**：能收到中断、序号在涨，就说明数据通路活了。
4. **实现 DEQUEUE 和 QUEUE**：用 benchmark 工具验证取数据、还数据能循环起来。
5. **加 mmap**：让用户态能直接读到数据内容，验证数值对不对。
6. **加 poll 和等待队列**：把轮询改成事件驱动，降低 CPU 占用。
7. **加溢出保护和重新提交**：这是长期稳定运行的关键。
8. **加错误处理和资源回收**：probe 回滚、release、remove 三条路径都要测。
9. **补诊断接口**：把槽位状态、队列深度、溢出计数暴露出来，方便板端排查。
10. **最后冻结 UAPI**：加版本号，写清每个字段的语义和取值范围。

每一步都在板子上实测过再往下走，比一次写完再调试快得多。
